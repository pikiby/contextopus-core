# PCW v3: контракты реализации

Версия плагина: **0.11.1**. Формат workspace: **1**. Это независимые номера. Обновление исходников не означает обновления установленного MCP.

## Открытие и создание

Все MCP-вызовы адресуют явные `work_root` и `workspace`. Новый `pcw_workspace_create` принимает `request_id`, полный согласованный `instructions_content`, `project_content`, `user_request`. Все четыре настройки должны присутствовать в YAML инструкций. Повтор идентичного запроса продолжает создание; другой запрос не заменяет существующее хранилище. Создание не запускает цикл и не создаёт задачу.

`pcw_workspace_inspect` проверяет выбранный каталог без миграции. `pcw_startup` принимает прежние `request_id`, `purpose`, `restart_cycle_id` и новые `invocation`, `task_id`. Workspace должен существовать и иметь поддерживаемый формат. Разрешены purpose `work`, `instructions`, `audit`, `rework`. Неявный запуск допускается только для work при разрешении в INSTRUCTIONS. Источник пользовательского сообщения аргументами MCP не удостоверяется.

`pcw_search`, `pcw_read`, `pcw_read_many`, `pcw_list`, `pcw_instructions_read`, чтение PROJECT, Current и истории не требуют `cycle_id`. Выбранные тексты читаются целиком. Чтение не создаёт отсутствующий workspace и не ремонтирует индекс; устаревшие индексные записи исключаются из выдачи и отмечаются pending. Блокировки и наблюдательный журнал являются служебными эффектами чтения.

## Совместимость

`format.json` находится в `.pcw/.control/<workspace>/`. Распознаваемый старый формат без номера имеет knowledge, пользовательский INSTRUCTIONS и конфигурацию индекса известной схемы. Нераспознанная структура или будущая версия блокируют открытие. Один поставляемый переход 0→1 добавляет отсутствующий PROJECT без выдуманных целей, пустой каталог current, при необходимости обновляет производный индекс и записывает номер после проверки. Прежний Current сохраняется буквально.

`pcw_upgrade_plan` выполняет предварительную проверку одним вызовом: возвращает совместимость, изменения, редакцию исходного набора, `pending_work`, `blockers` и `ready`. В незавершённой работе показаны request/task ID, названия временных материалов, темы предложений и их состояния. Открытая запись не удостоверяет наличие работающего агента. Редакция учитывает knowledge, tmp, указатель индекса и служебные записи; изменение черновика или цикла после просмотра требует нового плана.

`pcw_upgrade_apply(expected_revision, user_request)` под блокировкой повторяет проверку. Совместимые активные циклы переносятся с прежними ID, черновиками, редакциями и статусами; миграция не применяет предложения и не завершает работы. Неизвестные состояния, прерванные переходы starting/closing/restarting и повреждённые предложения перечисляются в плане как препятствия. Их восстановление — отдельная операция; отмена всех циклов не является шагом апгрейда.

Снимок в `control/backups/<id>/` содержит `workspace/` целиком, включая tmp и индекс, и `control/` со служебными данными, включая cycles.json и резервирование ID. Из control исключаются блокировки, квитанция текущей миграции и прежние резервные копии. Файлы снимка сверяются по хешам; исходные тексты, временные материалы и состояния циклов проверяются перед отметкой нового формата. Производный индекс может измениться; оставшаяся индексация возвращается отдельно в `pending_preparation`.

Операция сохраняется в migration.json. План незавершённой операции возвращает `resume_revision` и путь снимка: повтор использует эту исходную редакцию и тот же снимок, не перезаписывая уже сохранённые файлы. Конфликт исходников или повреждение снимка останавливает продолжение. Незавершённая миграция старой версии без нового формата снимка требует отдельного разбора сохранённой копии. Пакетный обход выполняет skill только по явно указанному списку/каталогам. Изменение смысла знаний и правил не является технической миграцией.

## PROJECT и Current

`pcw_project_update(cycle_id, content, expected_revision, user_request)` **подготавливает** предложение. `pcw_project_apply` применяет показанную редакцию под текущей политикой одобрения знаний. Это разделение сохраняет необходимость показать фактическое изменение до записи. Редактирование инструкций остаётся отдельным prepare/apply с обязательным одобрением.

`pcw_current_create` создаёт UUID задачи и связывает его с циклом; request_id обеспечивает повтор без дубликата. `pcw_current_list/read/update` работают с отдельными `current/<task-id>.md`. Поля: goal, constraints, verified_state, next_step, blockers, status. Статусы: active, blocked, completed, cancelled. Изменение требует прочитанной ревизии всего файла и привязки текущего цикла. Продолжение передаёт task_id при startup. Очистка tmp не удаляет Current; изменение PROJECT не переписывает задачи.

## Настройки и материалы

Настройки читаются только из YAML INSTRUCTIONS; смысловые правила остаются в его свободном тексте. Отсутствующие значения: allow_implicit_updates=false, knowledge_approval_required=true, git_history_enabled=false, material_max_tokens=null. При создании значения выбираются отдельно. Дубликаты и некорректные типы отклоняются.

`pcw_proposal_prepare` сохраняет прежние create/update/move/delete/merge/split операции. Дополнительное поле description задаёт краткое назначение темы. Чтение возвращает title, description и link_targets с подписями, сохраняя точные links. Необязательный from_id у read проверяет наличие реальной исходящей ссылки. Отдельного вызова модели для подписей нет.

При включённом material_max_tokens проверяется каждое конечное тело тем же токенизатором, что у индекса. Ответ needs_split содержит ID/ключи, фактические токены и предел. Применимого предложения и записи knowledge при таком результате нет. Семантические границы выбирает агент; токенные окна 512/64 остаются механизмом эмбеддингов. Метаданные не вызывают переиндексацию тела.

## Git

Настройка истории включает исходный снимок и снимки применений knowledge/INSTRUCTIONS/PROJECT. Под блокировкой в control/history сохраняется точный состав с текстами, затем Git строит дерево через отдельный индекс и локальный коммит. Чужие позднейшие файлы не читаются при повторе старого снимка. Очередь сохраняет порядок; одинаковое дерево не создаёт коммит. Tmp, Current, векторная база и аналитика не включаются.

Инструменты: history_list, history_diff, history_read, history_retry. Статус записи/индекса и статус Git разделены. Git pending не объявляется потерей уже сохранённого знания. Восстановление исторической редакции проходит обычное предложение по текущим правилам. Отправки в remote нет.

## SQLite и границы наблюдения

Общий MCP-dispatcher фиксирует начало и окончание обращения, параметры, результат/ошибку, длительность, режим и координаты в `.pcw/.analytics/events.sqlite`. Таблицы: events, blobs, versions, observed, imports, evaluations. SQLite WAL и блокировка workspace обеспечивают работу нескольких процессов; внешние редакторы могут не соблюдать эту блокировку.

Тексты после очистки секретов хранятся в blobs с отметкой редактирования. Versions связывает доступные тела и хеши до/после. observed_before_call означает наблюдение до текущего вызова, включая начальное обнаружение файла; автор не установлен. during_call означает изменение между наблюдениями вокруг вызова. Ошибка после записи файла может оставить только started; исход проверяется по редакциям. Единой файловой/SQLite-транзакции нет.

`analytics_query` выбирает события по workspace/task/cycle/tool/периоду/import, `analytics_read` — одно событие, `analytics_blob_read` — тело. Фиксируются реальные байты и время; токены и стоимость без измерения null. Ответы чтения самой аналитики не вкладываются повторно целиком в журнал. Оценки записываются отдельно через analytics_evaluate с критериями и ID доказательств.

`analytics_import` принимает явно выбранный файл и адаптер codex-jsonl либо pcw-session-v1. Импорт другой сессии поддерживается без изменения ядра; события хранят исходные координаты и не получают вымышленную корреляцию по времени. Нормализованный формат — JSONL с kind, timestamp, data и необязательным id, плюс указанный session_id. Встроенный Codex-адаптер читает публичные сообщения/вызовы и метаданные, исключая system/developer/analysis. Неподдерживаемый или повреждённый формат не выдается за проверенный импорт.

Фильтры секретов покрывают известные ключи, помеченные значения, bearer, приватные ключи и известные секретные переменные окружения. Произвольные непомеченные секреты надёжно распознать нельзя. Ошибки валидации MCP до входа в dispatcher, пропущенные обращения и ненаблюдавшиеся внешние действия не становятся событиями задним числом.

## Аудит и переработка

`pcw_audit` возвращает наблюдаемые дефекты формата, повтор ID/тела и отсутствующие цели ссылок, с фрагментами и редакциями. Смысловую проверку выполняет агент по инструкции, явно отделяя гипотезы. Постоянная память и индекс при аудите не меняются. Rework использует стандартные предложения; полный охват требует перечисления всех материалов области, а не одного top-N поиска.

## Проверка

Новые контракты покрываются test_workspace_v3.py, test_history_v3.py и test_analytics_v3.py вместе с прежними регрессионными тестами. Стандартный MCP проверяет реальный stdio-протокол. Реальные agent/model-прогоны отмечаются отдельно; успешный вызов инструмента не является доказательством универсального соблюдения инструкции моделью.
