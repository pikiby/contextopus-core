# Задача: обновление скиллов, MCP и организации контекста Contextopus

**Реализация:** Contextopus 1.1.0. Проверенные результаты и ограничения — в разделе 7; состав выпуска и установка — в [release notes](releases/1.1.0.md).

## Цель

Сделать Contextopus общей системой контекста для нескольких агентов и разных оболочек. Проекты, знания, цели и состояние работы должны находиться через общий поиск и связываться между собой. Подключение к центральному MCP должно восстанавливаться штатными средствами соответствующей среды.

Разделы 1–6 содержат согласованное задание. Раздел 7 фиксирует фактически выполненное и границы проверки.

## 1. Обновление скиллов

### Требуемый результат

- Сохранить основной вход `$w` и привести дополнительные команды к понятному единому виду `w-<действие>`.
- Выполнить ранее согласованное уплотнение: `$w`, `$w-search`, `$w-create`, `$w-settings`. Аудит, переработка и обновление формата вызываются через `$w` по смыслу поручения. По последующему прямому запросу анализ использования получает отдельный короткий вход `$w-analyze`; алгоритм остаётся единственным, в процедуре MCP.
- Дополнить набор отдельным коротким скиллом смыслового поиска проектов, описанным в разделе 4. Его окончательное имя выбрать при реализации в том же стиле; название `w-find` обсуждалось как вариант.
- Скиллы кратко направляют агента к канонической процедуре MCP. Полные алгоритмы не копируются в каждый скилл и каждую оболочку.
- Через `$w` доступны явно названные пользователем функции дополнительных скиллов: создание контекста, изменение инструкций, поиск и выбор контекста.
- При обновлении установки убирать распознанные старые управляемые команды, чтобы новые названия не добавлялись поверх прежних дублей. Пользовательские изменения и чужие скиллы сохранять; коллизии показывать отдельно.
- Проверять действительное обнаружение скиллов и инструментов клиентом, а не только наличие файлов и записей манифеста.

### Критерий приёмки

В каждой проверенной оболочке виден согласованный компактный набор команд. Скиллы вызывают существующие процедуры MCP; старые распознанные дубли не появляются рядом с новыми.

## 2. MCP: единый сервер, автозапуск и управление

### Общий принцип

Один центральный локальный HTTP MCP обслуживает несколько агентов и оболочек. Ядро, базы и модельные ресурсы общие. Завершение отдельной агентской сессии не завершает сервер. Решение проектируется для Linux, macOS и Windows; Codex является одним из клиентов.

### Жизненный цикл сервера

- Установка настраивает автозапуск через штатный пользовательский механизм ОС и восстановление процесса после сбоя.
- Сохраняются явные команды запуска, остановки и проверки состояния. Добавляется согласованное управление перезапуском.
- Повторный запуск не создаёт второго владельца тех же баз и модели.
- Главный TUI показывает состояние сервера и предоставляет действия запуска, остановки и перезапуска с понятным результатом. Он должен открываться и давать запустить сервер, когда MCP остановлен.
- CLI, TUI и установка используют общий механизм управления службой. Для запуска остановленного сервера не требуется обращение к этому же остановленному MCP.
- Диагностика различает: сервер остановлен, доступ запрещён средой, сервер доступен, подключение конкретного клиента не установлено. Ошибка доступа к HTTP не должна автоматически означать, что процесс остановлен.

### Восстановление клиентского подключения

Автозапуск сервера и восстановление MCP-подключения уже открытой сессии — отдельные операции.

- Сначала проверить, умеет ли клиент восстанавливать связь самостоятельно после появления или перезапуска сервера.
- Если требуется явное действие, использовать штатную возможность выбранной оболочки через её адаптер интеграции.
- Общий порядок: готовность сервера → переподключение клиента → получение инструментов → контрольный запрос через подключение нужной сессии.
- В установленном Codex обнаружен метод `config/mcpServer/reload` и подключение к работающему app-server через `codex app-server proxy`. Метод ставит обновление MCP открытых сессий в очередь; он не ограничен одним Contextopus. Прежде чем использовать его как готовое решение, проверить восстановление именно после неудачной инициализации и область воздействия на параллельные сессии.
- В интерфейсе предусмотреть действие переподключения для тех клиентов, где оно поддержано. Возможности и ограничения показывать по конкретному клиенту.
- Для Codex, Claude Code, OpenCode, Crush и последующих интеграций отдельно подтвердить действительный способ восстановления. Непроверенный или отсутствующий механизм не обозначать как работающий.
- Не пытаться заставить MCP-сервер управлять произвольными клиентами: восстановление соединения инициирует клиент или доступный механизм его интеграции.

Основание для метода Codex: [API app-server](https://learn.chatgpt.com/docs/app-server#api-overview). Контракт и поведение проверяются на фактически установленной версии.

### Критерии приёмки

- Один сервер доступен одновременно из нескольких клиентов; остановка одной сессии не затрагивает остальных.
- Проверены автозапуск и восстановление службы на заявленных платформах. Непроверенные платформы отмечены явно.
- TUI позволяет запустить остановленный сервер и показывает фактическое состояние после действия.
- В сценарии «клиент открыл сессию до запуска MCP» проверены появление инструментов и успешный вызов после поддерживаемого переподключения без потери истории беседы.
- Проверено поведение при перезапуске сервера во время существующего клиентского подключения.
- Ответ `/health`, HTTP 200 и запрос из отдельного процесса не подменяют проверку соединения целевой сессии.

## 3. Изменение процедуры Workspace: единые типизированные записи

### Устранение отдельного Current

Отдельный Current устраняется. Всё его содержимое переносится в `knowledge/` и работает по общим правилам материалов: сохранение, чтение, изменения, одобрение по настройке контекста, индексация, связи и история.

Переносятся поручение, ограничения, подтверждённое состояние выполнения, результаты, следующий шаг, препятствия и статус. Существующие идентификаторы сохраняются. Состояние незавершённой работы должно оставаться доступным после обновления.

Отдельные операции и процедура ведения Current заменяются общими операциями материалов. Агент получает идентификатор подходящей записи из поиска; знание ID заранее не является условием обнаружения работы. ID остаётся постоянным адресом для точного чтения, связей и обновления выбранной записи.

### Категории записей

В YAML хранится `type`. Например:

```yaml
id: stable-record-id
type: task
status: active
links:
  - related-record-id
```

Примеры назначения категорий:

- `knowledge` — сведения об устройстве и работе проекта;
- `task` — поручение и состояние его выполнения;
- `goal` — цель и условия её достижения;
- `project` — актуальное описание проекта и назначения контекста.

**Перечень открыт.** Определение категории — часть работы агента при подготовке материала. Агент проверяет используемые категории, выбирает подходящую и при необходимости вводит новую, избегая дублирующих названий. Пользовательские инструкции могут определять собственную классификацию и ограничения.

Инструменты принимают категории как данные; список доступных категорий получается из записей. При этом процедуры используют определённое назначение `project`, чтобы поиск проектов не смешивался со всеми остальными материалами.

Тип записи и принадлежность контексту — разные признаки. Тип отвечает на вопрос «что это за материал», контекст определяет его принадлежность и действующие правила работы.

### Общий поиск и связи

- Проекты, задачи, цели, состояние работы и знания доступны через общий RAG.
- Фильтры по контекстам и типам применяются до векторного отбора; для записей со статусом поддерживается соответствующая фильтрация.
- Результаты содержат ID, название, тип, контекст и данные, достаточные для выбора материала. Агент читает только нужные записи.
- Записи разных типов используют общие связи: задача может ссылаться на цель, проект, знания или другую задачу. Проверка ссылок, просмотр целей связей и обработка удаления распространяются на эти записи одинаково.
- При изменении материала обновляется его производный индекс. Содержимое, ссылки и результаты поиска не должны расходиться после миграции или изменения файла вне MCP.
- Поиск в других контекстах не меняет инструкции, выбранный рабочий контекст или место записи результатов.

### Описание проекта

Описание проекта также сохраняется как запись `type: project` и индексируется в общей базе. Поддерживается один актуальный источник описания, без отдельной вручную синхронизируемой копии для каталога или поиска.

Агент актуализирует описание по общим правилам, когда изменяются назначение, цели или границы проекта. Запись описывает текущий проект; после сохранения поиск использует обновлённое содержание.

### Общие инструкции

Переработать инструкции и процедуры под единые материалы:

1. Определять назначение и категорию записи при её создании или переработке.
2. Находить существующие связанные сведения и состояние работы через поиск, читать выбранное, затем решать вопрос изменения или создания материала.
3. Сохранять связанные материалы со смысловыми ссылками и понятным назначением этих связей.
4. Различать установленный факт, цель, поручение, план и подтверждённый результат. Индексация цели или задачи не превращает намерение в выполненную работу.
5. Поддерживать актуальное содержание и разумное смысловое разделение; не накапливать в материалах журнал каждого действия.
6. Сохранять действующие правила обязательных источников, согласования изменений и самостоятельность инструкций каждого контекста.
7. Не дублировать полную процедуру в скиллах, нескольких справочниках и пользовательских инструкциях. Краткий вход направляет к процедуре, а настройки и пользовательские правила остаются в своём источнике.

### Критерии приёмки

Обычный поиск находит перенесённое состояние работы без заранее известного task ID. Для задач, целей, проектов и знаний работают чтение, обновление, фильтры, связи, история и действующие правила согласования. Старый Current не остаётся отдельным рабочим хранилищем.

## 4. Выбор контекста и поиск проектов

Использовать существующий общий корень, каталог контекстов, реестр операций MCP и RAG. Не создавать самостоятельную поисковую систему или вручную поддерживаемый реестр проектов.

### Три операции

| Операция | Поведение |
| --- | --- |
| Перечислить контексты | Механически получить существующие папки контекстов в настроенном корне и вернуть названия и полные пути. Поддержать выбор по указанному имени или пути. Список автоматически отражает фактические папки. |
| Прочитать выбранный проект | Получить актуальную запись `type: project` указанного контекста. Чтение описания не требует уже запущенного рабочего цикла. |
| Найти проекты по смыслу | Выполнить общий векторный поиск с предварительным фильтром `type: project`, вернуть подходящие контексты и релевантные фрагменты описаний. |

Точные имена операций определить при реализации и зарегистрировать в существующем `contextopus_query`. Новый отдельный MCP-сервер для этого не нужен. Операции обнаружения контекстов должны работать до выбора конкретного Workspace.

### Процедура известного контекста

Пользователь указывает имя или путь → агент находит соответствующую папку → читает выбранное описание проекта → выполняет разрешённое действие. При нескольких совпадениях уточняет выбор. Он не читает подряд полные описания всех проектов.

### Процедура смыслового поиска

Пользователь не помнит названия или хочет разобраться, какие проекты и контексты у него есть → отдельный краткий скилл получает запрос → вызывает поиск по записям проектов → показывает подходящие контексты с фрагментами, поясняющими совпадение.

Запрос «найди» возвращает результаты. Явное поручение работать в однозначно указанном контексте позволяет перейти к работе. Неоднозначность разрешается с пользователем. Пустая выдача не создаёт новый контекст.

Выбор действует в рамках поручения конкретного агента. Общего переключателя активного контекста для всех параллельных сессий нет. Путь к памяти не выводится автоматически из имени репозитория или рабочего каталога.

### Критерии приёмки

- Контекст находится по имени и пути без обращения к эмбеддингам.
- Контекст находится по смысловому запросу без знания имени и без загрузки всех `PROJECT.md` в контекст агента.
- Изменение описания проекта отражается в последующем поиске.
- Список и поиск не создают отсутствующие контексты, не переключают чужие сессии и не изменяют инструкции.
- Отсутствующее описание отмечается как отсутствующее, а не заменяется выдуманным назначением по имени папки.

## 5. Обновление существующей системы

Переход включить в штатную процедуру обновления формата и установки:

1. Проверить исходные материалы, инструкции, записи Current, описания проектов, активные циклы и ожидающие предложения изменений.
2. Перенести Current и описания проектов в общий формат записей, сохранив ID, содержимое, статусы и возможность продолжить незавершённую работу. Ссылки и служебные привязки привести к новым адресам согласованно.
3. Обновить формат и индекс для новых типов. Проверить исходные файлы и результаты поиска, включая новые типы и межтиповые ссылки.
4. После проверки завершить отказ от отдельного Current и параллельного хранения описания проекта. Восстановимые технические снимки миграции не становятся вторым действующим источником.
5. Обновить скиллы, процедуры, манифесты и клиентские подключения. Учитывать распознанные старые имена, пользовательские правки и параллельно работающих агентов.
6. Обновление пользовательского INSTRUCTIONS проводить по действующим правилам его согласования; не заменять его новым шаблоном молча.
7. Проверить повторный запуск и продолжение прерванной миграции без дубликатов и потери данных. Неприменённые пользовательские предложения не применять и чужую работу не отменять ради обновления.

## 6. Порядок выполнения

1. Сверить текущие исходники, установленный пакет и реально подключённые клиенты; уточнить технические контракты без изменения согласованной модели.
2. Реализовать общие типизированные материалы, фильтры и связи; подготовить миграцию Current и описаний проектов.
3. Добавить перечисление контекстов, чтение описания и смысловой поиск проектов; обновить процедуру Workspace и короткие скиллы.
4. Реализовать управление центральным MCP, автозапуск и действия TUI; добавить поддержку переподключения через проверенные механизмы клиентов.
5. Выполнить проверки по разделам, затем проверить обновление существующей установки и данных.
6. В пределах разрешённого выпуска обновить поставляемые пакеты и клиентские установки, проверить свежие подключения и восстановление существующих сессий. Отдельно отчитаться об исходниках, установленной версии, миграции данных и фактической работе клиентов.

**Готовность задачи:** изменения согласованы между кодом, инструкциями, схемой хранения, поиском, связями, миграцией и поставкой; результаты проверки перечислены по средам, без подмены работоспособности наличием файлов.

## 7. Приёмка реализации

В исходниках реализованы шесть коротких скиллов, общие типизированные записи и фильтры, обнаружение проектов, миграция в формат 3, управление центральным MCP из CLI/TUI и клиентские способы восстановления соединения. Длительные MCP-операции выполняются в рабочем потоке, не блокируя проверку доступности сервера.

### Локальная установка и данные

- Установлен runtime 1.1.0. Новый клиент Codex обнаружил все шесть скиллов и выполнил реальное чтение через MCP. Для других клиентов различаются проверка конфигурации, подключение и вызов инструмента моделью.
- Пользовательская служба systemd включена и восстановила MCP после завершения процесса. Установленный TUI запустил остановленный сервер; проверка произведена без выхода и повторного входа пользователя.
- 22 из 27 контекстов перенесены в формат 3: 117 записей задач и 22 записи проектов включены в общий поиск; ID, инструкции, ожидающие предложения и 25 файлов состояния циклов сохранены.
- Пять старых контекстов оставлены без изменений: отсутствуют утверждённые инструкции; в трёх также конфликтуют старые ID. Эти условия не исправляются догадкой или отменой чужой работы.

### Восстановление клиентов

Исправлен транспорт Codex app-server proxy: действующий WebSocket обрабатывается через wsproto. Изолированная проверка использует этот же транспорт: две сессии с первоначально недоступным MCP после reload выполняют инструменты в тех же потоках, сохраняя непустую историю; последующий перезапуск MCP также переживается. В рабочей сессии отдельно подтверждены новые операции после перезапуска службы.

OpenCode восстановил соединение через свой API после первоначального сбоя и перезапуска сервера, сохранив историю. Эта проверка не запускала модельный turn и не заявляет вызов инструмента моделью. Для Claude Code и Crush сохранены их собственные способы и границы восстановления.

Содержимое установленного runtime сверяется с каноническими исходниками и ресурсами; release notes перечисляют совместимость и ограничения. ## Дополнение: Git как история графа материалов

Принятый объём: включить локальную Git-историю в стандартный набор новых контекстов; сначала предлагать весь набор настроек, затем при выборе собственного режима задавать отдельные вопросы. Существующие правила не переписываются автоматически. При подготовке изменений агент указывает краткий смысл коммита и явные merge/split/replace с исходными и результирующими ID. Эти сведения согласуются вместе с текстом и сохраняются в том же коммите. Поиск истории по ID, пути, дате и тексту, состав коммита и ограниченное чтение версии доступны через MCP. При пропаже прежнего условия, расхождении состояний, регрессии правил или вопросе о развитии проекта агент сначала проверяет подходящий участок истории. Старые редакции остаются свидетельствами, а не действующими правилами.

Дополнение реализовано в исходниках и установленном MCP. Операции доступны через штатные инструменты; тематические карточки project-update согласованы с реализацией. Проверка фиксации включает неизменённые снимки, повтор после сбоя, происхождение записей и ограниченные запросы истории.

## Дополнение: разделение Git и SQLite, анализ ограниченного периода

Git хранит версии постоянных текстов и объявленные преобразования материалов. SQLite хранит события, ошибки, длительности и проверенные ссылки на Git; отдельный производный индекс ускоряет поиск происхождения. Новые обращения не копируют весь контекст до и после каждого вызова. Тело прочитанного материала восстанавливается по коммиту, файлу и способу выделения фрагмента, только если проверены его хеши. Неподтверждённая ссылка не заменяется текущим содержимым.

Успешно зафиксированные служебные снимки после проверки полного дерева Git заменяются небольшими квитанциями. Ожидающие фиксации снимки сохраняются для точного повторения. Перенос старых SQLite-снимков выполняется ограниченными партиями через `analytics_migrate`: без удаления неподтверждённых или ещё используемых свидетельств.

`w-analyze` загружает единую процедуру MCP. До разбора задаются вопрос, контексты и период либо конкретная задача/цикл/импорт. Без заданных рамок инструмент выбирает последние семь дней. Курсор фиксирует фильтры и верхнюю границу записей; отчёт явно сообщает неполное покрытие. Фильтры редакции инструкций, версии пакета и процедур отделяют разные периоды правил. Прошлые действия оцениваются по сохранённым тогда инструкциям; неизвестное основание не заменяется сегодняшними правилами.

Проверяемые случаи: точное чтение старого текста и инструкций после изменения, чужой контекст при сохранении правил активного, отсутствие второго архива при выключенном Git, частичные выборки и продолжение, версии merge/split/replace, безопасное сокращение старых снимков и восстановление после прерванной фиксации. Подсчёт чтений не доказывает использование знаний моделью; токены и сравнительная эффективность требуют данных среды и отдельных сопоставимых прогонов.
