# Contextopus 1.0.0

Status: installed release candidate; cross-platform CI and final artifact verification remain required before publication.

Contextopus replaces the plugin-only delivery with a standalone application: `contextopus-core` distribution, `contextopus` import/CLI, private `pikiby/contextopus-core` repository. The source includes preexisting uncommitted 0.14.0/v4 work; HEAD before transition was 0.13.0. Release comparison must include that baseline.

## Changes

- Shared Application, typed Core/module operation registry and persistent data outside client plugin caches.
- Local HTTP MCP service as the single resource owner for clients, CLI and TUI.
- Workspace module preserves selection, independent reading, explicit/implicit updates, required sources, review, instructions approval and migration behavior.
- Thin native Agent Skills (`w`, `ws`, `wi`, `wc`, `wu`, `wa`, `wr`, `wx`) retrieve one canonical installed procedure.
- Project configuration adapters preserve unrelated settings and reject collisions; revision checks reject stale integration previews.
- Settings consequences and copy-only relocation receipts remain explicit.

## Local validation and installed candidate

- Full suite: 337 tests passed, 6 skipped. The only failures were two copied-legacy-launcher subtests because the ad hoc test interpreter lacked the standalone distribution. CI already installs it through `uv sync`. After installing the project into that interpreter, the targeted launcher/instructions/approval run passed: 34 tests and both stdio subtests. No test was bypassed to resolve this.
- After the final formatting pass, TUI/session adapter tests passed: 10. New model setup has CPU/CUDA/MPS selection, stale-plan and failure tests plus actual Application and HTTP MCP tests using real LanceDB and deterministic fake providers; these do not establish real GPU inference.
- Candidate wheel/sdist and four client bundles built successfully. `scripts/verify_release.py` verified all six assets, SHA256SUMS, required runtime/resources, canonical short skills and plugin version consistency.
- A new clean temporary environment installed the candidate wheel and 51 base packages. CLI version, runtime imports and canonical upgrade resources were checked from outside the checkout.
- The same wheel was installed into the user's uv tool environment with `[local] --torch-backend cpu`. Outside-checkout checks confirmed Contextopus 1.0.0, Torch 2.14.1+cpu and sentence-transformers 5.7.0. No model was instantiated by those checks. The actual existing Qwen revision, dimensions, normalization and Hugging Face cache were inspected and preserved.
- Eight short skills passed structural validation. Legacy entrypoint upgrades validate known shipped hashes or prior managed hashes; user edits and plugin cache paths are refused. Native cutover/default-root binding have targeted tests.
- Actual headless TUI captures use synthetic EXAMPLE data; see [capture provenance](../media/tui/README.md).

The repository was renamed to private `pikiby/contextopus-core`, origin updated, and the local checkout moved to `Documents/contextopus-core` with a compatibility symlink at its former location. The authorized live migration subsequently verified 27 contexts, 235 cards and a 20,932-file receipt; originals remain retained with old writes disabled. Exact current task, temporary work and knowledge bytes were checked. Five legacy contexts remain uninitialized until their complete instructions receive explicit review. Existing pinned Qwen CPU search/read succeeded after migration.

## Remaining release gates

Linux/macOS/Windows CI must pass before tagging/publication. Linux and macOS Python 3.12/3.13 jobs passed; Windows jobs exposed remaining migration portability defects, which are being corrected and retested. Fresh native Codex verified one Contextopus connection, four tools, core.status and the canonical upgrade procedure without a model turn. Plugin delivery exposes `contextopus:w` and the other namespaced skills; the installed direct native integration was selected for literal `$w` and the seven other bare short names, with both plugin caches preserved and disabled. Claude Code and OpenCode reported connected; OpenCode discovered all eight shared skills. Crush native server APIs independently reported the same eight skills and a connected four-tool MCP server. These checks establish native discovery/connection, not model-driven end-to-end task completion in every host. Final artifacts must be rebuilt from the CI-passing source. GraphFrontier and the skills registry remain future work. No PyPI publication is part of this delivery.

Cross-platform scope: Windows skips only the legacy 0.14 POSIX shell-launcher fixtures in `test_startup.py` (16 launcher tests; the pure version-bound check remains portable) and three `/bin/sh` integration tests in `test_contracts.py`. Portable manifest/resource checks and the new Core, Workspace, real LanceDB, HTTP MCP, model-setup and native configuration tests remain enabled. These skips describe the retained legacy plugin's shell launcher; they do not suppress standalone runtime failures.
