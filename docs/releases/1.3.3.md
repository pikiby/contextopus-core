# Contextopus 1.3.3 — Pending legacy work before initial rules

> Historical document: release/verification conditions below apply to the named
> version or dated check. The independent repository layout is unreleased; see
> [current development instructions](../development.md).

This narrow patch corrects legacy upgrade planning when initial rules are absent
and pending work is retained. The published 1.3.2 tag and assets remain unchanged.

## Fix

An upgrade preview could fail when a legacy context had no initial INSTRUCTIONS
but retained pending proposals. The instruction transition represented the old
body as absent; pending-work revision adaptation tried to hash that absence as
text. The failure occurred during planning, before migration application.

The correction adapts an old instruction revision only when the old instruction
body exists. Existing rules keep their revision checks. Initial rules still
require the normal reviewed content and confirmation under the effective policy.
This guard does not invent earlier approval, alter original reviewed proposal
bytes, approve or cancel pending work, or bypass migration conflicts.

Workspace format remains 4. The initial-rule/native-routing procedure, skills,
search settings and model configuration are unchanged from 1.3.2.

## Verification boundaries

The original missing-instructions reproduction failed before application with
`None.encode`. After the guard, the bounded affected set passed **30 tests** in
33.20 s, including both new registered-operation cases for missing and existing
rules. These checks preserve source bodies, original reviewed proposal bytes,
approval revisions and cycle state through preview, application and retry.
A prepared edit without an earlier rules basis still requires re-preparation;
the migration does not grant approval under newly initialized rules.

Version/release contracts passed **40 tests and two subtests** in 13.19 s after
aligning the repository's editable metadata. The separate complete MCP-contract
file passed **28 tests** in 5.07 s. These are bounded source checks, not a new full
platform suite. Release acceptance additionally verifies the exact packaged
wheel through the standard release/installed MCP checks and the changed legacy
regression outside the source checkout.

The earlier complete OS matrix remains attributed to `2add7fa`. The independently
reviewed controlled-corpus model turns belong to the 1.3.2 `f0578ce` runtime and
its wheel; unchanged procedure bytes are compared separately rather than
claiming new model turns or assigning that matrix to 1.3.3.

## Update and retry

Before changing the installation, retain a fresh coherent whole-set snapshot of
the current package, context data and client controls, including work completed
since earlier upgrades. Preserve the root, CPU/local extras, effective policies,
pending cycles and proposals, and one service owner.

After verifying the exact 1.3.3 artifact, follow `guide(procedure="upgrade")`
through a fresh preview and the accepted revision. Supply only the reviewed
initial rules where needed. Do not remove pending work or weaken approval rules
to make the migration pass. The [1.3 upgrade guide](1.3.0.md#direct-update-from-11-or-12)
describes the shared update and restore procedure.
