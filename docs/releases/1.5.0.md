# Contextopus 1.5.0 — Independent modules and native installers

Core now ships independently from Workspace and Session Search. Its wheel
contains the shared runtime, CLI/TUI/MCP, client adapters, module SDK and `m`
skill. Workspace 1.5.0 and Session Search 0.8.0 are separate module artifacts;
both require Core `>=1.5,<2`. Version 1.4.0 assets retain their earlier layout.

## Installation

- [Core-only installer](https://github.com/pikiby/contextopus-core/releases/download/v1.5.0/contextopus-core-1.5.0.zip):
  extract, run `sh install.sh` or `.\install.ps1`, choose a new data folder and
  optional clients. Local CPU dependencies and explicit model setup share the
  starter's verified installation path.
- [Starter bundle](https://github.com/pikiby/contextopus-core/releases/download/v1.5.0/contextopus-starter-1.5.0.zip):
  Core plus both modules. `--module none` selects Core only; repeat `--module ID`
  to select a subset. `--skip-model` defers weights and leaves search unready.
- `contextopus --root ROOT modules install ID --source PATH` installs a trusted
  built folder or ZIP through ordinary dependency, migration and enablement
  steps. `--plan` previews the checked payload without staging or activation.
  Existing module folders/state are refused; updates remain explicit and retain
  data/configuration. Changed bytes, unsafe paths, symlinks and identity or
  compatibility mismatches fail before publication.

Verify SHA-256 checksums from the same release before using the artifacts.
Internet is needed for dependencies and model weights. Selected module bundles
require Git; Core-only installation does not. Native client applications remain
separate prerequisites. See the [installation guide](../../distribution/README.md).

## Module infrastructure

Generic native contributions and persistent child services share Core's
operation registry, settings, procedures, skills and retrieval services. Storage
uses one Core-managed SQLite file per module, explicit migrations and bounded
transactions. Module SQL and RAG commits remain separate; modules own replay
and recovery bookkeeping. Disable retains records and files. Core has no
Workspace or Session Search installation branches.

## Upgrade and verification limits

The fresh installer refuses an existing tool/root, occupied default port or
existing service/root binding. It does not migrate or replace a live installation.
Failures retain a receipt and completed work; automatic resume/rollback is not
implemented. Existing installations require a coherent backup and isolated
migration review before an explicitly applied update.

Source and artifact checks exercise isolated roots, declared module operations
and test embeddings without changing the user's installation. They do not
establish native service, real model download or client reload acceptance on
every platform. Verify those steps on the target machine and inspect the result
rather than inferring readiness from an extracted archive or written config.
