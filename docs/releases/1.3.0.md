# Contextopus 1.3.0 — Compact retrieval and preserved context

> Historical document: release/verification conditions below apply to the named
> version or dated check. The independent repository layout is unreleased; see
> [current development instructions](../development.md).

This document describes the 1.3.0 candidate in this source tree. Publication, live installation, migration of user data and connection of existing user clients are separate acceptance steps; they are not established by a local build.

## Changes

- Place a module in `modules/` and install it through `$m`, CLI `modules install` or TUI Install. The shared Core operation prepares dependencies, applies the module's ordered SQLite migrations and enables compatible operations. Tables live in a common Core domain catalog; optional child-handler RPC provides scoped reads/writes without private database connections. Checksums, transactional migration and code/schema compatibility protect retries and updates. [Authoring guide and runnable example](../modules.md).
- The default MCP surface is `guide`, `read`, `write`. Obtain an applicable procedure once, reuse it through ordinary work, and request only an unknown operation signature. Compact presentation runs after journaling; `detail="full"` preserves operation evidence and explicit fragments preserve text.
- Material search groups document keys before relevance boundaries and result limits for all five builtins. Builtin algorithm versions are 2.0.0; saved algorithm choices and parameter defaults remain. Diagnostics distinguish candidate limits, relevance cuts, result caps and retained-snapshot limits. Replay uses the current implementation on recorded candidates and identifies incomplete historical evidence.
- Ordinary material responses expose author descriptions and labelled navigation targets, with paths/context and actionable faults. New records and changed bodies require reviewed author descriptions; migration does not fabricate descriptions for old cards.
- Workspace format 4 keeps stable YAML IDs, restores Obsidian navigation and moves recognized machine policy flags into existing Core configuration. Free-form user rules, required sources, graph endpoints and unfinished work are preserved.
- Lightweight settings reads establish effective reread policy before preparation. Repeated `w` continues the current task/cycle; independent retrieval creates no work cycle. Settings and rules retain current review/approval requirements.
- A tmp update still requires its exact current revision. Malformed revision, missing material and well-formed stale revision now identify distinct recovery reads. A verified historical failure came from an inserted character in the submitted hash; the server does not silently repair it.
- Windows lock acquisition no longer writes to an empty lock file before acquiring the byte-range lock. This removes the pre-lock write that could raise `PermissionError` when processes initialized storage simultaneously; existing seeded lock files remain compatible.
- Persisted base-context records, Unicode settings/receipts, native link aliases and public module/algorithm metadata are decoded as UTF-8 independently of the OS default. Byte-sensitive comparisons preserve LF/CRLF; algorithm Python sources follow their declared encoding. Windows CI checks these dataflows and coherent restore early, then runs the full suite and installed-package checks.

## Direct update from 1.1 or 1.2

An intermediate 1.2 installation is not required. Package version 1.3.0 and Workspace format 4 are different version domains. Follow the installed `guide(procedure="upgrade")` and preserve the chosen root and client delivery mode.

1. Inventory the actual executable/version, service PID/root, client tools/skills, contexts, effective policy values, IDs, links/sources, description gaps, Git/history, cycles, tmp and immutable pending proposals/approval revisions. Do not infer the live package from a source checkout.
2. At a coherent point, retain a recoverable **whole-set backup**: old package/extras, Core configuration, context files/rules, Git, consistent SQLite backups, RAG, cycles/tmp/proposals and client configuration/managed manifests. Stop or coordinate writes while capturing databases; do not copy changing database files arbitrarily. Retain old plugin caches for sessions still using them.
3. Exercise the same direct transition on an isolated copy. Verify IDs, rules, policy values including false/0/null, graph endpoints, required sources, historical evidence and pending-work continuation. Check repeated and interrupted migration. Format readiness and description completeness are separate results.
4. Only after installation is authorized, verify the exact wheel against its SHA256SUMS and replace the old package while retaining extras. For example, with the verified local artifact:

   ```console
   uv tool install --force --python 3.12 ./contextopus_core-1.3.0-py3-none-any.whl
   ```

   Preserve `[local]` or other extras already required by that installation. Coordinate the existing single service owner; do not run a second owner against shared data. Keep the existing root and use its explicit upgrade preview/apply procedure rather than initializing an empty replacement.
5. Apply reviewed format changes; retry interruptions with the original retained migration revision/snapshot. Preserve cycle IDs and immutable proposal bytes. Technical overlays must not transfer old approval to changed meaning; a non-equivalent conflict blocks the affected apply and gives a reprepare path. Do not cancel another agent's work.
6. Preview and apply managed client integration in the previously selected direct/plugin mode. For a direct Codex user integration:

   ```console
   contextopus --root <existing-root> integrate codex --user
   contextopus --root <existing-root> integrate codex --user --apply
   ```

   Other client names are claude-code, opencode and crush. Known unchanged 1.1/1.2 skills are recognized even without a prior managed manifest. User-modified/unrecognized skills remain protected; resolve the reported collision rather than overwriting them. Preserve unrelated client settings and credentials. Refresh the procedures used after update.
7. Restart/reload through the client's supported mechanism. From each targeted actual client verify the exact package/process/root, discover `guide/read/write`, obtain the procedure, then search and read the chosen context. Native discovery/recovery checks do not establish that a model followed the procedure. Report publication, package installation, running owner, client connection and model-behavior verification separately.

For a deliberate old-client transition, `CONTEXTOPUS_LEGACY_TOOLS=1` advertises the old aliases alongside the current tools. The default advertises only three tools. Never retry a failed mutation under another alias: its first attempt may already have committed. Upgrade the client or deliberately select compatibility.

## Retry and restore

Keep the exact preview/migration/proposal revision for idempotent retry; inspect a conflict before preparing another revision. Retry indexing or captured Git history separately from a successful text save. A missing description is repaired through an author-reviewed proposal from actual content, not an automatically clipped heading.

If rollback is required, stop the new owner and restore the old **package, data, settings and client configuration together** from the coherent backup. Restore database/index state through its supported snapshot method. Never launch 1.1 against incompatible converted 1.3 data or activate two writable owners. Validate the restored root, pending work and actual client path before resuming writes. Preserve failed-transition artifacts for diagnosis.

## Artifacts and evidence limits

The intended artifact set is one wheel, one source archive, four client skill bundles and SHA256SUMS. Local build/verification checks identity, packaged resources, entrypoint and bundle bytes. A clean temporary wheel installation is distinct from a user upgrade. CI declares Linux/macOS/Windows with Python 3.12/3.13; only executed jobs establish those platform results. Model behavior, description quality, Obsidian UI behavior and live client adoption require their own evidence.
