# Contextopus 1.2.0

Contextopus 1.2.0 makes the shared runtime extensible and search easier to inspect. Add a module from a folder, choose how retrieved candidates are selected, and inspect the settings and evidence behind a search. Bundled product guides are ordinary searchable Workspace records with protected updates.

[Changes since 1.1.0](https://github.com/pikiby/contextopus-core/compare/v1.1.0...v1.2.0) · [Release assets](https://github.com/pikiby/contextopus-core/releases/tag/v1.2.0)

## Install modules and keep their data

Root-local modules have explicit prepare, enable, disable and update actions in MCP, CLI and the TUI. Dependency preparation stays separate from activation; updates preserve module data/configuration and retain the previous release for recovery. Enabled modules can contribute operations, procedures, skills and search algorithms. The included Synk example reads the installed command's version without starting synchronization.

## Choose search behavior and inspect its evidence

Five built-in algorithms cover distance jumps, distance thresholds, a fixed nearest count, no additional selection and Archivist-style selection. Enabled modules can add algorithms using the shared descriptor/implementation contract.

Settings inherit through algorithm defaults, root, module, context and one request. Preview the effective values and their sources before applying a persistent change; request-only overrides remain local. Exact and semantic catalog discovery help find an algorithm. Search evidence distinguishes eligible documents, candidate fragments, selected results, cutoffs and capture limits. Bounded event analysis and replay compare another selection using recorded candidates without generating new embeddings; replay does not establish answer quality.

## Search the product guides without changing task rules

The bundled documentation context contains installed-version information, module/algorithm guides, examples and templates for context instructions. Explicit init/model setup installs it after an embedding profile is ready and refreshes the algorithm catalog. A first init without a model reports `model_setup_required`.

The documentation role can point at another existing context. Reading guides never switches the active task's context or instructions. Updates retain custom instructions, user-added links and retired documents; edited or deleted managed documents return a conflict with incoming text. Interrupted installation and indexing resume from their exact saved plan. Delivery failures remain visible without invalidating a successfully installed model.

## Separate instruction approval and find contexts with `w-context`

`instructions_approval_required` independently controls approval of instruction edits. It defaults to `true`, including when absent from existing instructions. If the current value is false, the displayed revision can be applied without an additional prompt. A proposed change to false cannot bypass the current true policy. An instruction edit still requires the user's direct request.

The discovery skill is now `w-context`; material search stays `w-search`. Integration retires recognized managed `w-find` copies, preserves user-edited or foreign skills and reports collisions. Existing runtime identifiers and pending proposals remain compatible.

## Install or update

Install [uv](https://docs.astral.sh/uv/getting-started/installation/), download the wheel and `SHA256SUMS` from the release assets, and verify the wheel's SHA-256 digest against that manifest. From the download directory:

```console
uv tool install --python 3.12 ./contextopus_core-1.2.0-py3-none-any.whl
contextopus --version
contextopus init
```

For an existing installation, add `--force`. For local embedding inference, use the same verified wheel with its optional extra: `"./contextopus_core-1.2.0-py3-none-any.whl[local]"`. This release uses GitHub assets; it does not assume PyPI publication.

1. Keep the existing data root and the extras already used by the installation. Restart its shared service with `contextopus --root <existing-root> service restart`.
2. Run explicit `contextopus --root <existing-root> init` and inspect the returned `setup` outcome. With no profile, preview `setupmodel`, then run `setupmodel --apply` after authorizing the model operation. Pending delivery, conflicts or approval requirements identify the next operation and exact plan. Legacy `.pcw` roots follow the existing explicit relocation procedure first.
3. Use the normal Workspace upgrade procedure for older context formats. Customized INSTRUCTIONS, unfinished work and pending proposals are preserved. Missing instruction-approval settings remain restrictive.
4. Preview `contextopus --root <existing-root> integrate <client> --project <project>` and repeat with `--apply` for that reviewed integration. Retain the chosen direct or native-plugin delivery mode. Refresh managed skills so `w-context` replaces recognized `w-find` copies.
5. Reload the actual client and verify its connection and selected context. Successful packaging or configuration writes do not establish a reconnected client.

Outside setup, catalog refresh is explicit through `core.algorithms_refresh`. Semantic catalog queries report stale/missing cards instead of silently refreshing them. Saved legacy search parameters remain supported; choosing another algorithm starts from that algorithm's defaults.

## Artifacts and verification limits

Release artifacts comprise the Python wheel, source archive, four client skill bundles (`codex`, `claude-code`, `opencode`, `crush`) and `SHA256SUMS`. The wheel contains runtime code, procedures, skills and the documentation bundle. Installation does not replace a live data root automatically.

[Repository verification evidence](../implementation/modules-search-1.2.md) records Linux checks with offline embedding providers and temporary roots, including real local indexing, MCP transports, module subprocesses, policy transitions, safe updates and isolated wheel installation. The new TUI images use synthetic fixtures.

The CI matrix is configured for Linux, macOS and Windows with Python 3.12 and 3.13. Configuration alone does not establish that a release revision passed on every platform. Local checks do not establish native login startup on all operating systems, a model-driven client turn, semantic-quality improvements or token savings. Check the release workflow results separately from these repository-level tests.
