# PCW: управляемая память проекта — целевая архитектура

> Примечание: личные пути и идентификаторы трасс/материалов обезличены; результаты измерений сохранены.

Историческая версия. Для общего RAG, категорий, YAML ID, sources и миграции действует [v4](context-workspace-design-v4.md).

Статус: руководящая схема версии 0.11.0 по принятым решениям обсуждения. Реализация и проверка описаны в [плане](context-workspace-upgrade-plan.md), [цели](context-workspace-upgrade-goal.md) и [отчёте проверки](context-workspace-v3-verification.md); конкретные API — в [контрактах](context-workspace-v3-contracts.md). Предыдущая версия 0.10.0 описана в [v2](context-workspace-design-v2.md); изменение исходников не обновляет установленный плагин автоматически.

## 1. Назначение

PCW — переносимая память для работы над любыми проектами через MCP. Она хранит точные сведения, установленные принципы, закономерности и процедуры, а также явно принятые решения с их основаниями. Агент получает нужную часть накопленного контекста, использует её прежде повторного исследования и исправляет обнаруженное устаревание.

Основной результат — меньше повторного выяснения устройства проекта и меньше ненужного текста в контексте агента. Запись отчёта о каждом действии не является целью памяти. Одобрение гипотезы не превращает её в установленный факт.

PCW не определяет агентную среду, не выбирает модели исполнителей и не управляет их запуском. Работа напрямую и делегирование определяются поручением и применимыми инструкциями среды. Нативный идентификатор сессии не нужен для работы памяти.

С версии 0.12.0 MCP-интерфейс состоит из двух инструментов: `pcw_query` для чтения и `pcw_execute` для изменений. Конкретная операция выбирается параметром `operation`, её параметры передаются в `arguments`, а `work_root` и `workspace` задаются отдельно. Описания и схемы операций доступны по запросу через `pcw_query(operation="describe")`; они не публикуются десятками отдельных инструментов. Разрешённые операции и их параметры проверяются до обращения к хранилищу. Существующий dispatcher сохраняет проверки и журналирование под именем конкретной операции. Формат workspace не меняется.

## 2. Разделение данных

Целевая структура выбранного контекста:

```text
<work_root>/.pcw/<workspace>/
  INSTRUCTIONS.md       # правила работы и настройки пользователя
  PROJECT.md            # назначение, цели, требования, границы проекта
  current/<task-id>.md  # актуальное состояние отдельной задачи
  knowledge/<id>.md     # самостоятельные смысловые материалы и связи
  tmp/<cycle-id>/       # рабочие результаты и подготовленные изменения
  .pcw-runtime/         # производный векторный индекс и конфигурация
  .git/                # история постоянных данных, если включена

<work_root>/.pcw/.control/<workspace>/
  ...                  # состояния операций и защита от конфликтов
  format.json          # версия формата и состояние технического перехода
<work_root>/.pcw/.analytics/
  events.sqlite        # журнал наблюдаемых обращений к PCW
```

Новые имена служебных файлов и API в этом документе — проект контрактов реализации. Существующий filename-ID материала сохраняется: перенос или изменение заголовка не меняет идентичность. Перенос ID в YAML отменён и в обновление не входит.

| Данные | Порядок использования и изменения |
| --- | --- |
| INSTRUCTIONS | Читаются полностью перед работой. Единственное действующее место проектных правил. Редактирование по прямому поручению с показом и подтверждением редакции. |
| PROJECT | Читается при входе в проект. Заполняется из целей и границ пользователя. Изменяется по его поручению; собственная новая редакция агента сначала предъявляется человеку. Порядок задаётся INSTRUCTIONS. |
| Current задачи | Выбирается только для выполняемой задачи. Содержит поручение, ограничения, подтверждённое состояние, следующий шаг, препятствия и статус. Агент обновляет состояние при существенных изменениях, сохраняя смысл поручения. |
| Knowledge | Используется через поиск и выборочное чтение. Изменяется по политике данного workspace; сохраняет актуальное описание, а не последовательность отчётов. |
| Tmp | Дополнительный рабочий контекст данного цикла. Не имеет силы утверждённых правил или знаний. Не включается в обычный поиск и Git-историю памяти. |
| Журнал и Git | Доказательства действий и предыдущие редакции. Читаются для конкретной задачи разбора; не подмешиваются в обычный векторный поиск. |

PROJECT, INSTRUCTIONS и записи Current не дублируются в knowledge и не требуют эмбеддингов. Правила их ведения задаются одним источником в INSTRUCTIONS; технические проверки реализуются в коде.

## 3. Выбор контекста и создание

Сохраняются установленные пользователем координаты `work_root` и `workspace`. Новый вопрос, смена рабочего каталога, единственный найденный каталог и пустая выдача не разрешают создание или переключение. Если выбор потерян или неоднозначен, агент спрашивает. Единого переключателя для всех параллельных сессий нет.

Открытие существующего контекста и создание должны стать разными операциями. Чтение и обычный startup не создают отсутствующее хранилище. Проектируемый `workspace_create` вызывается только процедурой создания после выбора пользователя; проверяет отсутствие цели и повторяет тот же запрос идемпотентно.

`pcw-create` принимает место и назначение в обычной форме. Для неизвестного размещения показывает конкретные существующие варианты и их полные пути либо принимает путь пользователя. Отдельными вопросами получает ещё не выбранные настройки:

1. Можно ли агенту самому начинать обновление этого контекста?
2. Нужно ли подтверждать подготовленные изменения knowledge?
3. Включать ли автоматическую Git-историю постоянных данных?
4. Какой предел размера материала использовать? Варианты в порядке: **1024 токена — рекомендуется**, **Другой предел**, **Без ограничения**. Число уточняется только при выборе другого предела без указания значения.

Первым предлагается стандартный предел из шаблона INSTRUCTIONS: **1024 токена основного текста**. Поскольку чтение возвращает материал целиком, пять материалов дадут до 5120 токенов до учёта метаданных. Это практический начальный предел, а не измеренный оптимум и не требуемый размер каждой записи. Агент ждёт выбора пользователя; молчание и предварительно выбранный в интерфейсе вариант не считаются ответом. Обновление плагина не переписывает настройки существующих контекстов.

Уже указанные значения не переспрашиваются. Затем агент показывает начальные INSTRUCTIONS и PROJECT. Создание использует сразу согласованные редакции. Не возникает промежуточного workspace с неподходящими настройками. Создание контекста само по себе не начинает выполнение проекта; `current/` первоначально пуст.

## 4. Чтение и обновление — разные основания запуска

`pcw-search` можно использовать для поиска по необходимости, без полного рабочего цикла. Он открывает выбранный существующий контекст только для чтения, получает действующие инструкции, ищет материалы и читает нужные темы и связи. Такой поиск не создаёт tmp, задачу Current, предложение записи или обязанность завершать рабочий цикл.

Для этого чтение инструкций, PROJECT, метаданных, поиск и чтение материалов должны работать без обязательного `cycle_id`. Отсутствующий workspace возвращает ошибку, а не создаётся. Восстановление индекса и миграция не выполняются скрыто ради чтения. Служебный аналитический журнал может записывать факт обращения; знания и настройки остаются неизменными.

Самостоятельное начало обновления и подтверждение записи управляются независимо в INSTRUCTIONS:

| `allow_implicit_updates` | `knowledge_approval_required` | Поведение |
| --- | --- | --- |
| false | true | Обновление по поручению; применение после показа и подтверждения. |
| false | false | Обновление по поручению; показ и применение без вопроса. |
| true | true | Агент может начать разбор результатов и предложить изменения; применение после подтверждения. |
| true | false | Агент может начать разбор, показать и применить изменения. |

Отсутствие нового разрешения на самостоятельный запуск сохраняет прежний запрет. Отсутствие настройки одобрения в старых инструкциях сохраняет требование подтверждения. Недопустимое значение настройки отклоняется. Политика самостоятельного обновления не разрешает смену контекста, изменение инструкций или расширение пользовательской задачи.

Плагин проверяет значения политики и ревизии. Параметр, переданный моделью, сам по себе не доказывает человеческое происхождение поручения или подтверждения.

## 5. Основной цикл и дополнительные процедуры

```text
Выбрать процедуру и установленный контекст
  → прочитать INSTRUCTIONS, PROJECT и нужный Current
  → найти и прочитать нужные знания
  → выполнить поручение; сохранять рабочие результаты в tmp
  → сопоставить результат с knowledge по действующим правилам
  → подготовить и показать изменения либо обоснованный no_changes
  → применить по политике; завершить разбор; закрыть цикл
```

Рабочий цикл начинается по явному вызову либо разрешённой политике самостоятельного обновления. Предыдущие разовые разрешения не переносятся на новый вызов. Постоянные настройки действуют, пока пользователь их не изменил.

Основной skill маршрутизирует функциональное поручение, не требуя точного имени мини-скилла:

| Поручение | Процедура |
| --- | --- |
| Найти сведения | `pcw-search` |
| Создать контекст | `pcw-create` |
| Изменить правила | `pcw-edit-instructions` |
| Обновить формат старого контекста | `pcw-upgrade` |
| Проверить качество контекста | `pcw-audit` |
| Переработать выбранные знания | `pcw-rework` |
| Разобрать использование памяти агентом | `pcw-analyze` |
| Выполнить задачу с памятью | Основной цикл `pcw` |

Скилл описывает процедуру, INSTRUCTIONS — проектные правила, MCP выполняет операции. Агент загружает только нужную процедуру. Обычный поиск внутри основного цикла не требует заново загружать поисковый skill. Обнаружение проблемы не даёт полномочий запускать следующую процедуру; составное поручение «проверь и исправь» допускает обе.

Код проверяет допустимость операций выбранного режима, ревизии, ссылки и политику применения. Аудит не имеет пути применения изменений knowledge. Полный цикл может вести назначенный субагент с чистым контекстом: он сам читает инструкции и знания; основной агент передаёт вопросы, результаты и реальные подтверждения пользователя. Обычные исполнители возвращают результаты агенту цикла для tmp.

После работы обязателен разбор результатов для памяти, но запись может оказаться ненужной. Показ выполняется в языке чата и содержит фактические изменения текста и связей. Ссылка на файл, UUID и перечень тем не заменяют этот показ. Незавершённое согласование, применение, индексация и неразобранные результаты удерживают цикл открытым.

Startup и finish очищают только tmp адресованного цикла; данные параллельных циклов сохраняются. Применение knowledge не очищает tmp. Отдельного вопроса о разрешении закрыть завершённый цикл нет. Current задачи сохраняется после очистки.

## 6. Материалы и навигация

Самостоятельный материал отвечает на самостоятельный вопрос. Если разделы обычно нужны для разных запросов, это основание разделения. Объяснение сохраняет свои условия, основания и пределы достоверности. Общая тема может быть связана с частными; размер файла не заменяет оценку смысла.

Конкретная процедура сохранения: агент сравнивает вывод с найденными темами, составляет отдельные итоговые материалы и связи, затем передаёт их одним предложением create/update/delete/merge/split. Существующее большое описание перерабатывается тем же механизмом: прочитать целиком, распределить самостоятельные вопросы, сохранить условия, подготовить новые темы и судьбу исходного ID, проверить входящие ссылки. Простое обрезание текста не допускается.

При включённом пользователем пределе `proposal_prepare` считает токены каждого конечного тела тем же токенизатором, который используется для индекса. Возвращает превышающие материалы, фактический размер и предел до записи. Значение и режим настраиваются; общий обязательный числовой предел этим документом не устанавливается. Проверка объёма не определяет смысловые границы.

Материалы делит агент по смыслу. Код нарезает уже готовый текст для эмбеддингов токенными окнами с перекрытием. Qwen остаётся стандартным источником эмбеддингов, поддерживаются заменяемые модели и API. Новая модель для определения смысловых границ не вводится.

Чтение возвращает полный выбранный материал. Рядом со ссылками выводятся ID и понятные подписи назначения целевых тем; они получаются из сохранённого заголовка и краткого описания, подготовленного вместе с темой, без отдельного модельного вызова при каждом чтении. Изменение подписи проходит обычную подготовку материала. Содержание соседей загружается по выбору агента.

Автоматическое рекурсивное раскрытие и графовый поиск не входят в принятую схему. Для аналитики необязательный `from_id` обозначает заявленный переход по существующей ссылке; журнал отличает это от обычного чтения. Наличие перехода не доказывает правильность использования текста.

## 7. PROJECT и состояние задач

PROJECT содержит назначение, цели, требования и границы проекта. Current имеет отдельный файл для каждой задачи, а не один общий файл всех сессий. `task_id` выдаёт PCW при создании задачи; он не вычисляется из идентификатора агентной сессии.

Контракты реализации: `project_read/update`, `current_create/list/read/update`. Создание Current требуется для порученной работы, но не для справочного чтения. Список возвращает короткие сведения, а читается только выбранная задача. Продолжение использует известный task_id; при неоднозначности агент уточняет выбор. Пустой поиск знаний не создаёт новую задачу.

Обновление принимает `expected_revision` и проверяет её под блокировкой. Current меняется после существенного результата, нового препятствия, уточнения поручения, смены следующего шага или статуса. Он хранит актуальное состояние, не журнал каждого вызова. Завершение цикла и завершение долгой задачи различаются: следующий цикл может продолжить тот же task_id. При изменении PROJECT прежние задачи не переписываются автоматически.

## 8. Git-история

Git включён в предлагаемый стандартный набор нового контекста. Пользователь может принять набор целиком или настроить отдельные параметры. После создания с включённой историей сохраняется начальный снимок. Каждое завершённое применение изменений постоянных данных создаёт один коммит; пустое сравнение не создаёт коммит. Включаются knowledge, INSTRUCTIONS и PROJECT. Tmp, индекс и аналитический журнал не входят в снимок. Задачная запись Current не подменяет историю знаний.

`history_list` фильтрует коммиты по ID материала, пути, сообщению и датам; `history_search` ищет появление или удаление точного текста; `history_changes` показывает изменённые файлы и объявленные преобразования. `history_diff` и `history_read` возвращают выбранный фрагмент с явными границами. В Git trailers коммита сохраняются ID материалов, операция, цикл и объявленные merge/split/replace. Эти связи образуют историю происхождения материалов даже после полного переписывания текста. Сходство файлов не заменяет объявление преобразования; старые коммиты без него так и обозначаются. Агент обращается к ним, когда выясняет причину расхождения, изменение требования, происхождение текущей формулировки или готовит восстановление. Прошлые версии не индексируются как действующие знания и не становятся текущими инструкциями. Восстановление — обычное показанное предложение по текущей политике.

Успешная запись данных и Git-коммит имеют отдельные статусы. При сбое Git повторяется фиксация уже записанного состояния. Под блокировкой сохраняется состав и редакции этого снимка: последующее чужое изменение не должно незаметно попасть в коммит прежней операции. Отправка истории в удалённый репозиторий не подразумевается.

## 9. Аналитика действий

Основной вариант — SQLite-журнал, который заполняет код плагина при обращениях к MCP, без дополнительного поручения агенту «запиши действие». Одна локальная база на work_root различает workspace, цикл, задачу и операцию. Анализатор может читать выбранные чужие циклы и импортированные сессии; он не ограничен собственной сессией.

Минимальные группы записей:

- обращения: время, процедура, инструмент, параметры, результат, ошибка, длительность и состояние завершения;
- затронутые материалы: ID, версии до/после, путь, текст или ссылка на сохранённый текст;
- связи: возвращённые соседние темы и заявленные переходы `from_id`;
- фиксации: operation ID, commit, изменённые пути и проверяемый diff;
- необязательный импорт истории среды: источник, исходные идентификаторы и координаты сообщений, вызовов, ответов;
- результаты анализа отдельно от объективного журнала: критерий, оценка и ссылки на доказательства.

Большие тела можно хранить отдельными артефактами с хешем и ссылкой из SQLite. Одних хешей недостаточно для восстановления содержания: нужный текст или соответствующая Git-редакция должны сохраняться. Секреты исключаются из параметров и тел до записи; место исключения отмечается, чтобы не выдавать очищенный журнал за полную запись.

Запись начала и результата операции различается. Если процесс прервался между изменением файла и записью результата, журнал показывает неопределённый исход, который сверяется с ревизиями. SQLite и файловая запись не объявляются общей атомарной транзакцией.

MCP-журнал видит обращения к PCW. Прямые изменения файлов, пропущенный вызов и ответ пользователю требуют истории среды и/или снимков файлов. Git показывает изменение между редакциями, но не доказывает автора и не сохраняет автоматически незакоммиченные промежуточные состояния. Импорт привязывает события только при наличии основания; несовпавшее остаётся несопоставленным.

Отчёты выбирают контексты, задачи, циклы, инструменты и период. Они позволяют сравнивать время, ошибки, повторные чтения, объём переданных материалов и путь до применения. Отсутствующее измерение токенов или стоимости не заменяется выдуманной оценкой. Аналитика отделена от knowledge и используется по задаче анализа.

## 10. Обновление старых контекстов

Версия формата хранится отдельно от версии плагина. Проверка совместимости выполняется при открытии конкретного контекста. Обновление плагина без изменения формата не переписывает память.

`pcw-upgrade` определяет последовательность поставляемых переходов формата, показывает затронутые файлы, сохраняет восстанавливаемое состояние, применяет и проверяет переходы. Новая версия отмечается после успеха. Повтор продолжает незавершённую операцию. Для старого контекста без номера версия определяется по проверяемым признакам; неоднозначность не разрешается догадкой.

План миграции одновременно показывает совместимость, конкретные незавершённые работы и препятствия. Совместимые открытые циклы, их tmp и предложения сохраняются с прежними идентификаторами, редакциями и статусами. Апгрейд не требует отменять работу, не применяет черновики и не закрывает циклы. Восстановимый снимок включает workspace и отдельные служебные данные циклов; их целостность проверяется до отметки нового формата. Несовместимое или повреждённое состояние требует отдельного восстановления. Разбор старых задач не подменяет обновление формата.

Пакетный режим работает только с указанными пользователем контекстами или каталогами. Нет скрытого обхода всего компьютера. Несовместимое открытие сообщает о необходимой процедуре, не запускает её внутри поиска или аудита.

Код мигрирует технический формат, сохраняя знания, ID, связи и пользовательские настройки. Разделение прежнего Current или смешанного файла на цели и знания — содержательная переработка. Она выполняется отдельной процедурой с показом изменений. Новый стандартный шаблон не заменяет пользовательские инструкции. Если доступны прежний шаблон, пользовательская редакция и новый шаблон, они могут помочь подготовить предложение; применение правил остаётся процедурой pcw-edit-instructions.

## 11. Аудит и переработка

`pcw-audit` проверяет выбранную область без изменения постоянных данных. Каждое замечание содержит материал, ревизию, конкретный фрагмент, проблему и основание: правило, противоречащий материал, отсутствующую цель ссылки. Установленная ошибка отделяется от предположения, требующего исследования. Отчёт можно отдать другому агенту или использовать позже с проверкой актуальности ревизий.

`pcw-rework` выполняет пользовательское преобразование: удалить указанную информацию, уплотнить, оставить отношения, раскрыть конкретную связь или привести знания к новым инструкциям. Агент составляет перечень всей затрагиваемой области. Для требования «всю информацию» обход не ограничивается векторным top-N. Нужные изменения готовятся штатным предложением с обработкой входящих ссылок, показом и применением по политике.

Аудит сам не запускает исправления. Изменение INSTRUCTIONS само не перерабатывает knowledge. Если расширение связи требует новых данных, исследуются разрешённые источники; недостающий механизм не выдумывается. Технический аудит проверяет ссылки и формат, а смысловой разбор выполняет агент с действующими правилами и основаниями.

## 12. Границы принятого решения

В обновление включены смысловые материалы с настраиваемым пределом, подписи связей, свободное чтение, раздельные политики обновления и одобрения, создание с выбранными настройками, PROJECT и Current задач, Git-история, SQLite-аналитика, миграция, аудит, переработка и маршрутизация процедур.

Не выбраны как основная реализация: JSONL/DuckDB вместо SQLite, обязательная внешняя телеметрия OpenTelemetry, автозагрузка всех соседей, отдельный общий реестр агентных сессий, производные контексты и специальные представления базы. Они не являются скрытыми пунктами плана.

Основания: непубличное обсуждение архитектуры, пользовательское замечание о связях и последующее обсуждение миграции, аудита, переработки и ансамбля skill в этой сессии. Для предела материала учтены последние явные «одобрено» и «Принято»; прежний отказ не выдан за действующее решение. Имена новых параметров и методов конкретизируют реализацию принятой схемы, а не описывают уже выпущенный API.

## Обязательные внешние источники

При создании контекста задаётся отдельный вопрос о ссылках, требующих актуальной проверки. Ответ сохраняется как create_required_sources в INSTRUCTIONS. При согласии туда включается стандартное правило создания ссылок; критерии авторства остаются в этом файле. Уже существующие контексты автоматически не переписываются.

Такая ссылка оформляется в теле материала блоком required_sources: точный URL и ограниченный вопрос extract. Любое получение материала требует нового обращения к каждому отмеченному источнику. Это относится и к повторному чтению в одной задаче, независимо от разрешения создавать новые ссылки. Агент извлекает только ответ на вопрос и необходимые условия; загрузка сайта целиком не требуется. Обычные цитаты и связи между материалами не включают эту процедуру. Недоступный источник отмечается как непроверенный. Исполнение — обязанность агента по скиллу; плагин сохраняет блок, но не выполняет HTTP-запросы за агента.

## Самоанализ использования памяти

`pcw-analyze` разбирает выбранную работу по журналу PCW и, когда она предоставлена, истории агентской среды. Он показывает доказательства поиска, чтения, переходов по связям, изменений и ошибок; отдельно отмечает границы наблюдения. Факт чтения не доказывает использование знаний в результате. Анализ не изменяет знания, не начинает рабочий цикл и не подменяет сравнительные испытания отдельного стенда.
