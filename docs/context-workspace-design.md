# PCW: формирование и использование контекста

> Примечание: личные пути и идентификаторы трасс/материалов обезличены; результаты измерений сохранены.

**Отдельная версия руководящего документа от 17 сентября 2026 года.**

Основа — [предыдущий руководящий документ](../.pcw/project-update/knowledge/plugin-update-design.md). Он сохранён отдельно без изменений. Эта версия определяет целевую схему PCW как рабочей памяти основного агента. Она не является отчётом о реализации, выпуском плагина или подтверждением соответствия установленного кода. Ссылка на основу относится к локальному документу проекта; его наличие в опубликованном репозитории не предполагается.

Главное изменение: PCW не требует выполнять исследование, изменения и проверки внешних источников через субагентов. Основной агент может выполнять эту работу сам либо делегировать по указаниям пользователя и правилам своей среды. Обращение к накопленному контексту и сохранение новых знаний обязательны при обоих способах работы.

Подготовка эмбеддингов автоматическая: основной агент сохраняет обычные материалы knowledge, плагин нарезает их алгоритмом по токенам с перекрытием, а выбранный источник вычисляет векторы. По умолчанию это локальная `Qwen/Qwen3-Embedding-0.6B`; её можно заменить другой моделью или API эмбеддингов. Отдельная модель для определения границ не используется.

## 1. Цель

PCW сохраняет полезный контекст между задачами и сессиями и позволяет получать именно те сведения, которые нужны для текущей работы. Основной агент сначала использует накопленные знания, затем дополняет их результатами работы и обнаруженными уточнениями.

Память должна уменьшать повторное исследование источников и объём прочитываемого контекста. Для этого знания сохраняются отдельными крупными смысловыми блоками, связываются точными навигационными ссылками и индексируются по токенным фрагментам с перекрытием внутри каждого материала.

PCW отвечает за контекст, его хранение, поиск и актуализацию. Выбор исполнителей, распределение внешней работы, запуск внешних исполнителей и организация проверок принадлежат пользователю, основному агенту и среде исполнения. Использование памяти не навязывает единую схему организации этой работы.

## 2. Кто что делает

| Участник | Ответственность |
| --- | --- |
| Основной агент | Обращается к контексту, оценивает его применимость, выполняет работу сам или делегирует, формирует новые знания и управляет всей памятью через MCP. |
| Необязательный исполнитель внешней работы | Выполняет конкретное разрешённое поручение и возвращает факты, результат и ограничения проверки основному агенту. Не управляет PCW. |
| Источник эмбеддингов | Вычисляет векторы подготовленных фрагментов и поисковых запросов. По умолчанию — Qwen; источник можно заменить. Не определяет границы и не редактирует знания. |
| Плагин и MCP | Сохраняют материалы, адресуют их по ID, применяют явные изменения ссылок, автоматически нарезают текст по токенам с перекрытием и обновляют поисковую базу, возвращают фактические статусы операций. |

### Память принадлежит основному агенту

Основной агент сам читает knowledge, сохраняет новые материалы, обновляет Current, исправляет содержание, выполняет уплотнение, меняет ссылки и удаляет заменённые материалы. Эти действия не передаются исполнителям внешней работы. Для сохранения основной агент передаёт обычный текст материала; границы, массивы фрагментов и отдельные поручения для индексации он не готовит.

Источником новых знаний может быть собственное исследование основного агента, выполненное им изменение или проверка, сведения пользователя либо содержательный результат необязательного исполнителя. Происхождение фактов и границы их проверки сохраняются. Для записи собственных наблюдений не требуется создавать фиктивное поручение, запускать субагента или указывать вымышленный идентификатор исполнителя.

### Организация внешней работы

Основной агент вправе самостоятельно читать разрешённые исходные файлы, исследовать данные, применять разрешённые изменения и проверять результат. PCW не добавляет обязательного посредника между основным агентом и реальными источниками.

Если выбрано делегирование, основной агент передаёт самостоятельное поручение: что сделать, необходимые факты текстом, разрешённые исходные объекты, ограничения, критерии проверки и что вернуть. Субагенту не передаются ID и пути материалов knowledge, Current, журнал PCW или инструкции управления памятью. Он получает отдельный контекст задания и не наследует диалог основного агента с его инструкциями PCW.

В поручении явно запрещается использовать инструменты PCW и обнаруживать, читать или менять `.pcw`. Это граница на уровне поручения. Техническая изоляция инструментов и файловой системы этим документом не объявляется реализованной. Исполнитель возвращает результат основному агенту; все решения о сохранении и изменении общей памяти принимает основной агент.

Определение и регистрация окружения агента не входят в PCW. Плагин не требует собирать версию клиента, перечень доступных агентных моделей и инструментов, уровни рассуждения или параметры запуска исполнителей, сохранять снимок окружения либо строить карту инструментов и моделей. Эти сведения не являются условием открытия памяти, поиска, записи или индексации.

PCW не запускает внешних исполнителей и не требует регистрировать их поручения, выбирать модель по собственной карте, связывать сессию исполнителя или назначать отдельного проверяющего перед чтением и записью контекста. Профиль **модели эмбеддингов** из раздела 3 задаётся конфигурацией источника эмбеддингов; он не требует определения окружения агента.

### Короткий цикл обращения к памяти

Инструкции и вызовы, выполняющие операции, разделяются. Уже прочитанные неизменившиеся инструкции не возвращаются целиком при каждой операции. Обычный ответ записи содержит ID, ревизию, ссылки, статус и конкретные незавершённые действия; большие тексты возвращаются при содержательном чтении, а не при каждом служебном переходе.

Плагин проверяет записанное состояние внутри операции и сообщает результат. Если ответ подтверждает проверенную запись нужной ревизии, немедленно повторять тот же вызов чтения только ради подтверждения не требуется. Основной агент читает содержание для оценки смысла либо при неопределённом результате. Пакетные операции допустимы для независимых материалов, с отдельным статусом каждого элемента и честным указанием частичного выполнения.

Открытие workspace возвращает Current, сведения о незавершённых операциях памяти и материалы, ожидающие подготовки. Полная история действий, старые результаты и настройки, которые не нужны для текущей работы, автоматически в контекст не загружаются.

### Пользовательская команда и границы разрешения

Для работы с памятью сохраняется единый skill `$pcw`; отдельный `$pcw-run` не нужен. Подготовка контекста сама по себе не запускает описанную в нём будущую задачу. Чтение инструкции, ссылка на источник или сохранённый план не создают разрешения менять внешний объект, устанавливать компоненты, публиковать результат или делать Git-коммит. Учитываются действующие указания и уже предоставленные разрешения пользователя.

### Запуск MCP и подготовка компонентов

MCP остаётся интерфейсом инструментов PCW. Его локальный сервер объявлен в переносимом формате: корневой `plugin.json` и корневой `mcp.json`. Codex подставляет установленный путь в аргумент `${PLUGIN_ROOT}/scripts/launch.sh` до запуска `sh`; команда не ожидает, что переменная уже существует в окружении. Совместимые метаданные `.codex-plugin/plugin.json` сохраняются, но не объявляют повторный старый транспорт через `mcpServers`. Отдельная ручная регистрация через `codex mcp add` не требуется. Python-код работы с knowledge, current, ссылками, LanceDB и эмбеддингами не заменяется другой реализацией из-за ошибки запуска.

Плагин использует явно выбранный существующий Python либо доступный `python3`. Обязательного пути к отдельному `venv` нет. При запуске плагин не создаёт Python-окружение, не устанавливает пакеты и не скачивает модель. Это не означает, что он может работать без необходимых компонентов.

При вызове `$pcw` основной агент проверяет доступность MCP. При недоступности сам выполняет предусмотренную ограниченную диагностику установленного плагина и его зависимостей. Работа с PCW не передаётся субагентам. Результат ошибки подключения не подменяет установление её причины.

Если компонента нет, основной агент сообщает, что требуется установить и где. При уже предоставленном разрешении выполняет согласованную установку; при его отсутствии запрашивает разрешение пользователя. Отсутствие самого Python также обрабатывается этим сценарием: разрешённая установка интерпретатора, затем проверка необходимых библиотек. Установка библиотек относится к тому же выбранному Python, который будет запускать PCW.

Новый `venv` автоматически не создаётся. Для системного Python, пакеты которого защищены операционной системой, допустима явно согласованная установка библиотек в отдельную папку пакетов PCW, подключаемую существующим интерпретатором. Это не новый интерпретатор и не виртуальное окружение. Защита системных пакетов не отключается; готовность зависимостей нельзя подменять успешностью обновления файлов плагина.

После разрешённой установки основной агент повторяет проверку запуска и подключения MCP. Он проверяет результат и продолжает исходное поручение. При выпуске плагина проверяется свежая сессия настоящего Codex: обнаружение инструментов и вызовы PCW через Codex, включая чтение, запись и поиск. Ручное добавление переменных пути в тест сервера не заменяет эту проверку. Успешный отдельный тест сервера не означает, что уже восстановлено его подключение в текущем клиенте Codex. Переподключение выполняется только реально доступным механизмом клиента; если клиент требует перезапуска текущей сессии, агент прямо сообщает об этом, сохраняя исходное поручение для продолжения. Несуществующая команда автоматического перезапуска не предполагается.

Отказ пользователя, отсутствие прав, сети, места или ошибка установки возвращаются как конкретное препятствие. Агент не устанавливает компоненты в обход отказа и не объявляет подготовленный текст сохранённым, если запись не состоялась. Сохранённые материалы knowledge остаются источником истины; сбой индексации не означает их удаления, а готовность MCP сама по себе не означает готовность локальной модели.

Для локального поиска отдельно учитываются библиотеки модели и первая загрузка весов Qwen. Если загрузка ещё не разрешена, основной агент сообщает о ней и запрашивает согласие. Последующие обращения используют загруженную модель в работающем процессе; новое окружение и новая загрузка модели для каждого текста не создаются.

## 3. Какие данные существуют

### Реальные источники

Файлы проекта, код, документация, данные и другие разрешённые объекты существуют независимо от PCW. Их может исследовать основной агент или необязательный исполнитель. Накопленный контекст описывает наблюдавшееся состояние источников; сам по себе он не доказывает, что оно не изменилось.

### Материал knowledge

Материал — обычный читаемый Markdown-файл с полезными сведениями по самостоятельному предмету. Его содержание может включать текст, таблицы, код, условия, ограничения и координаты источников. Обязательный шаблон смыслового содержания не вводится. Основной агент передаёт материал в MCP цельным текстом, без разметки границ эмбеддингов и без массива частей. Если сведения вернул субагент, основной агент сохраняет их по тем же правилам.

Основной агент **до сохранения** разделяет новые сведения на крупные самостоятельные смысловые блоки и сохраняет каждый блок отдельным материалом. В одном материале остаются связанные факты, необходимые условия и ограничения. Архитектура, независимые правила хранения данных и отдельная функция экспорта не объединяются в один общий отчёт только потому, что получены за один запуск.

Критерий разделения материалов — смысл и ожидаемое использование: поиск по одному предмету должен приводить к материалу об этом предмете, а не заставлять читать весь отчёт. Токенная нарезка относится только к поисковым фрагментам внутри файла и не определяет тематический состав файлов knowledge. Не требуется превращать каждый факт в отдельный файл.

Между полезными для совместного чтения материалами основной агент создаёт ссылки по разделу 8. Сначала сохраняются обычные материалы, затем плагин автоматически нарезает текст **внутри них** на токенные окна с перекрытием. Уменьшение частей в индексе не исправляет чрезмерно широкий исходный материал: результат поиска по-прежнему адресует этот материал целиком.

MCP генерирует уникальный ID нового материала и использует его как имя файла `.md`. Основной агент не придумывает имя-ID. При исправлении того же предмета идентификатор сохраняется. Время сохранения фиксируется в UTC; версия содержания и происхождение сведений позволяют различать наблюдения. Данные об исполнителе добавляются только при действительном делегировании и установленной идентичности. Для фактов, полученных основным агентом, идентификатор субагента не нужен.

Содержательное знание отличается от истории выполнения. Квитанции «файл создан», «Current обновлён», границы частей, ожидания и повторы вызовов не становятся материалами knowledge. Полный внешний артефакт может требоваться для проверки, но его копия не обязана попадать в память. Сохраняются новые знания, необходимые координаты артефакта и фактические ограничения; операционное состояние учитывается отдельно.

### Фрагмент для эмбеддинга

Фрагмент для эмбеддинга — буквальный непрерывный участок уже сохранённого материала, выделенный алгоритмом по числу токенов. Соседние фрагменты перекрываются: конец предыдущего входит в начало следующего. Их назначение — найти материал по запросу; они не заменяют сам файл и не являются новыми пересказами. Семантическая завершённость каждого фрагмента не гарантируется.

Плагин использует настроенный токенизатор, размер окна и величину перекрытия, извлекает исходные фрагменты и передаёт их источнику эмбеддингов. Основной агент и субагенты не выбирают границы. Отдельные файлы для этих частей не создаются.

### Векторная база

Тексты токенных фрагментов хранятся в LanceDB, в тех же строках, что и вычисленные по ним векторы. Состав одной строки:

```text
ID материала knowledge + исходный текст фрагмента + эмбеддинг этого фрагмента + текущий путь к материалу
```

Строка также привязана к ревизии содержания, позиции фрагмента и настройкам нарезки: индекс относится к конкретному состоянию текста. Один фрагмент — одна строка. У одного материала может быть несколько строк: каждая содержит исходный текст своего фрагмента и его вектор, но один и тот же ID исходного материала. Участки перекрытия намеренно присутствуют в соседних строках. Отдельные файлы для выделенных частей не создаются. Сохранённые в базе части и их векторы служат поиску; полный исходный материал knowledge остаётся источником знаний.

Ссылка ведёт на сохранённый материал knowledge, а не автоматически на реальные файлы, по которым получены сведения. Это два разных уровня источников.

Поиск возвращает ID материалов и их текущие адреса. Инструмент чтения принимает ID и открывает соответствующий материал целиком. Адрес в поисковой базе — производные данные для доступа к файлу, а не неизменяемый идентификатор. Списки связей между материалами берутся из knowledge; отдельная таблица отношений как самостоятельный источник истины не вводится. Близость векторов означает возможную полезность материала, но не подтверждает его актуальность и не доказывает наличие нужного ответа.

### Утверждённая связка для первой реализации

- Векторная база — LanceDB OSS. Она встраивается в процесс плагина и хранит данные в локальной папке; отдельный сервер базы не требуется. Ссылка на материал knowledge хранится вместе с вектором как служебное поле и позволяет адресно находить записи для обновления. [Документация LanceDB](https://docs.lancedb.com/quickstart).
- Модель эмбеддингов по умолчанию — `Qwen/Qwen3-Embedding-0.6B`. Это мультиязычная модель размером около 0,6 млрд параметров, предназначенная в том числе для текстового и кодового поиска. Стандартная размерность вектора — 1024; поддержка меньшей размерности не означает, что её сокращение уже выбрано для PCW. Qwen вычисляет векторы; нарезку текста выполняет алгоритм плагина с токенизатором выбранной модели. [Описание Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).

Основание выбора — отсутствие отдельного сервера для локальной базы и опубликованные результаты мультиязычного поиска Qwen при небольшом размере модели. Выбор для первой реализации утверждён. Скорость и потребление памяти измерены на одном целевом компьютере, а качество поиска — на зафиксированном наборе материалов PCW; результаты приведены в [отчёте](search-assessment.md). Этот отчёт относится к прежней схеме подготовки и не подтверждает качество новой токенной нарезки с перекрытием. Сравнительное преимущество над другими связками не измерялось.

### Источники эмбеддингов и локальный вариант по умолчанию

По умолчанию плагин использует `Qwen/Qwen3-Embedding-0.6B` локально через `sentence-transformers`. При первом обращении к эмбеддингам работающий процесс плагина загружает модель и сохраняет её в памяти для последующих вызовов. На каждый текст отдельный процесс и повторная загрузка модели не создаются. При завершении процесса модель выгружается; следующий запуск снова загружает её. Первое получение весов требует загрузки из источника модели; дальнейшая работа может использовать локальный кеш. Подмена локальной модели внешним сервисом при ошибке запрещена.

Источник сменный: пользователь может выбрать другую локальную модель либо внешний API эмбеддингов, указав адрес, модель и ключ доступа. Нарезка при этом остаётся алгоритмом плагина. Единый вызов источника принимает список подготовленных плагином текстов и назначение `document` или `query`, возвращает по одному числовому вектору на каждый текст в исходном порядке. Основной агент этот список не формирует. Поддерживаются:

- Локальный адаптер `sentence-transformers`: вызывает загруженную модель.
- Ollama: отправляет `model` и `input` в `/api/embed`, получает `embeddings`; задаёт `truncate: false`, чтобы сервер не отрезал текст молча.
- HTTP API, совместимый с `/v1/embeddings`: отправляет `model` и `input`, читает `data[].embedding` с учётом `index`. Адрес сервера и имя переменной окружения с ключом задаются явно. Для другого протокола нужен отдельный адаптер.

Подключить можно любой источник, который действительно возвращает эмбеддинги и для протокола которого есть адаптер. Разговорная модель и подписка на чат сами по себе таким источником не являются. Подписочный сервис допустим только при наличии разрешённого программного интерфейса эмбеддингов. Ключи не записываются в knowledge и Git; платный API не включается автоматически из-за наличия подписки Codex.

Конфигурация разделяет подключение к источнику и свойства пространства векторов. Подключение задаёт адаптер, адрес или локальный путь, ссылку на секрет. Профиль эмбеддингов задаёт модель и её ревизию, размерность, оформление входа для запроса и документа, нормализацию и другие параметры вычисления. Активная таблица LanceDB связана с этим профилем и настройками отсечения кандидатов. Одинаковое количество чисел не означает совместимость векторов разных моделей или вариантов вычисления.

Настройки нарезки отдельно задают токенизатор и его версию, размер окна `chunk_size_tokens` и перекрытие `overlap_tokens`. Токенизатор соответствует выбранной модели; для внешнего API он задаётся в конфигурации адаптера вместе с допустимой длиной входа. Нельзя считать токены другой модели токенизатором Qwen без установленной совместимости. Конкретные численные значения размера и перекрытия этим документом не фиксируются; правила их применения заданы в разделе 5.

Для Qwen используется оформление запроса из раздела 6, исходные фрагменты передаются без поисковой инструкции. Другой источник использует собственный явно настроенный формат, а не обязательно инструкцию Qwen. Размер окна учитывает допустимую длину входа выбранной модели, включая служебные токены и оформление документа. Адаптер сообщает об ошибке при неподдерживаемом размере входа или некорректном ответе; молчаливое усечение и фиктивные векторы не допускаются. Локальный адаптер проверяет длину токенизатором модели, Ollama получает `truncate: false`. У совместимого с `/v1/embeddings` API нет общего параметра запрета усечения: выбранный сервер должен отклонять слишком длинный вход. Клиент не может установить по полученному вектору, обрезал ли такой сервер текст скрыто.

### Переключение источника эмбеддингов

Переключение выполняется по явному распоряжению, а не автоматически в ходе поиска.

1. Плагин принимает новое подключение, профиль модели и совместимые настройки токенной нарезки. Источник без интерфейса эмбеддингов отклоняется без изменения действующей базы.
2. Если изменились модель или настройки нарезки либо совместимость вычислений не установлена, плагин приостанавливает векторный поиск и обновление поисковых данных на время переключения.
3. При неизменных настройках нарезки и допустимой длине частей использует сохранённые в LanceDB фрагменты актуальных ревизий. Если изменились токенизатор, размер окна, перекрытие или допустимая длина входа, заново нарезает исходные материалы алгоритмом. Вычисляет векторы новым источником и записывает их в новую, пока неактивную таблицу. Пересказ, участие агента в выборе границ и изменение knowledge не требуются.
4. После окончания одним обновлением активной конфигурации переключает и источник, и таблицу. Векторы запроса и материалов всегда вычисляются совместимым профилем. Параметры расстояния для новой модели задаются отдельно; прежний подобранный порог не объявляется подходящим автоматически.
5. Удаляет прежнюю поисковую таблицу и возобновляет работу. Knowledge, его ID и навигационные ссылки не меняются. Новая таблица во время переключения — средство замены индекса, а не архив прежних состояний.

Если вычисление новых векторов завершается ошибкой, новая таблица не активируется; плагин продолжает работать с прежним источником и таблицей и сообщает об ошибке. Изменение только ключа доступа не требует новых эмбеддингов. Смена адреса или способа запуска без пересчёта допустима только при установленной совместимости вычислений; совпадение названия модели, в частности при переходе на квантованный вариант, её не устанавливает.

### Применение изменений и сохранение прежних состояний

При наличии разрешения прежние состояния knowledge сохраняются через Git основным агентом. Git служит средством просмотра истории и отката изменений; отдельное хранение прежних состояний векторной базы ради отката не вводится. После восстановления knowledge из Git фрагменты в базе, векторы и ссылки должны соответствовать восстановленному состоянию.

Каждое изменение применяется сразу в затронутой части: изменение содержания обновляет материал и его поисковое представление; изменение только списка ссылок обновляет навигационные данные, но не требует нового эмбеддинга текста. После завершения подготовки поиск должен учитывать новые и изменённые записи и не возвращать удалённые или заменённые варианты. Между записью изменённого текста и окончанием подготовки материал имеет явный статус ожидания; старые части не выдаются как актуальные. Эмбеддинги неизменённых материалов заново не вычисляются. Порядок переназначения ссылок и удаления заменённых материалов описан в разделе 8.

В LanceDB OSS создание и обновление ускоряющего векторного индекса вызывает код плагина. Обновление этого индекса — отдельная операция над уже вычисленными векторами, а не повторное получение всех эмбеддингов. Пока новые или изменённые записи не включены в индекс, обычный поиск LanceDB дополнительно просматривает их напрямую. Поэтому полная перестройка индекса после каждого изменения не требуется, а поиск не должен использовать режим `fast_search`, пропускающий записи вне индекса. [Индексация LanceDB](https://docs.lancedb.com/indexing/vector-index).

Требование немедленного физического освобождения места на диске снято. После замены или удаления записи её прежние данные могут физически оставаться в файлах LanceDB, но не должны возвращаться в текущей поисковой выдаче. Освобождение занятого ими места относится к отдельному техническому обслуживанию базы и не является условием завершения каждого изменения. [Поведение операций изменения и удаления LanceDB](https://docs.lancedb.com/tables/update).

Семидневное хранение прежних состояний базы ради отката не вводится: историю обеспечивает Git. Изменения и техническое обслуживание выполняются во время работы плагина над запросом, без отдельного постоянно работающего процесса. Точная периодичность обслуживания здесь не устанавливается.

### Current

Current содержит пять полей: цель, ограничения, условие завершения, текущий шаг и блокер. Его ведёт основной агент в соответствии с фактическим запросом пользователя. При отсутствии блокера поле пусто. Изменение формулировки цели не должно незаметно менять разрешённый объём работы.

Current нужен для восстановления фокуса между сессиями, а не для регистрации каждого действия или управления внешними исполнителями. Он обновляется при существенном изменении шага, состояния или препятствия; повторная запись неизменившихся полей не требуется. Незавершённые операции памяти сохраняются отдельно и не теряются при обновлении Current.

Чтение Current не заменяет поиск нужных знаний и не доказывает завершение задачи. Для использования памяти не требуется обязательный реестр внешних поручений или завершённый цикл управления субагентами.

## 4. Общий цикл задачи

1. Основной агент определяет фактический запрос и разрешённые границы работы. Открывает подходящий workspace, восстанавливает Current и учитывает незавершённые операции памяти.
2. **Прежде всего, до исследования внешних источников, обращается к накопленному контексту:** формулирует векторные запросы, читает отобранные смысловые материалы, при необходимости переходит по ссылкам. Уже доступные и неизменившиеся сведения повторно не читает. Если база пуста, фиксирует отсутствие контекста и продолжает работу.
3. Оценивает достаточность, применимость и актуальность найденных сведений. При недостатке контекста уточняет поиск; недостающие факты устанавливает по реальным источникам. Не повторяет бесконечно поиск, который уже не дал нужных сведений.
4. Выполняет разрешённую работу сам либо делегирует по выбранной схеме. Способ исполнения не меняет правил обращения с памятью. Проверяет существенный результат по реальным объектам подходящим для задачи способом.
5. **По мере получения содержательных результатов** выделяет новые факты, изменения прежних сведений, условия и ограничения проверки. Сопоставляет их с затронутым knowledge, устраняет установленные ошибки и повторы, формирует самостоятельные смысловые материалы. Не откладывает все знания до финала длительной задачи.
6. Сам сохраняет изменения через MCP и выстраивает нужные ссылки. Для фактов, полученных непосредственно основным агентом, применяется тот же порядок; отдельный возврат исполнителя не требуется. Полный повтор знаний не создаёт новый файл.
7. Плагин автоматически нарезает сохранённый текст новых или изменённых материалов по токенам с перекрытием, получает векторы от выбранного источника и обновляет базу. Для этого основной агент не передаёт текст повторно, не формирует массив частей и не запускает помощника. Неизменившиеся материалы при прежних настройках не переиндексируются.
8. Проверяет фактические статусы сохранения и поиска, обновляет Current при необходимости и сообщает результат пользователю. Незавершённое сохранение, подготовка или проверка обозначаются явно; успешное внешнее действие не превращает их в завершённые операции памяти.

Если новых знаний или уточнений нет, создавать материал ради формального завершения не требуется. Если задача прервана, сохраняются уже установленные полезные сведения и конкретное незавершённое состояние. PCW не требует отдельного проверяющего или нового внешнего поручения ради завершения этого цикла.

## 5. Подготовка материалов для векторного поиска

Основной агент сохраняет обычный материал knowledge цельным текстом. Нарезка для эмбеддингов выполняется кодом плагина по токенам с перекрытием. Qwen по умолчанию вычисляет эмбеддинги полученных фрагментов; отдельной языковой модели, поручения или возвращаемого агентом массива границ в этом процессе нет.

1. После сохранения нового или изменённого материала плагин берёт сохранённый текст и его ревизию. Нарезка и индексация запускаются автоматически в рамках обработки записи; повторное чтение и передача того же текста основным агентом не нужны.
2. Плагин применяет токенизатор выбранной модели и настройки `chunk_size_tokens` и `overlap_tokens`. Размер окна — положительное целое число; перекрытие — положительное целое число меньше размера окна. Окно с оформлением входа должно укладываться в лимит модели. Недопустимая конфигурация возвращает ошибку, а не молча меняет настройки.
3. Алгоритм последовательно выделяет окна до `chunk_size_tokens` токенов с шагом `chunk_size_tokens - overlap_tokens`. Следующее окно включает конец предыдущего. Последнее окно может быть короче; после достижения конца материала дополнительных окон из одного перекрытия не создаётся. Непустой текст короче окна образует один фрагмент, пустой — ни одного.
4. Фрагменты извлекаются из исходного текста по соответствующим позициям с сохранением символов, пробелов и переводов строк. Текст не пересказывается и не нормализуется; покрывается полностью и в исходном порядке. Повторяются только участки предусмотренного перекрытия. Нарезка не меняет Markdown-файл knowledge.
5. Выбранный источник получает подготовленные плагином фрагменты и вычисляет их эмбеддинги. Плагин записывает в LanceDB текст каждого фрагмента, его вектор, позиции, ID материала, ревизию и настройки нарезки.
6. Перед публикацией поисковых записей плагин проверяет, что ревизия материала и настройки остались актуальными. Результат для устаревшего текста или прежних настроек не становится действующим индексом. Состояние `indexed` сообщается только после фактического обновления всех частей данного материала.

Границы определяются числом токенов и могут проходить внутри абзаца, таблицы или блока кода. Перекрытие переносит часть соседнего контекста, но не гарантирует смысловую завершённость каждого окна. Полный материал сохраняется без изменений. Тематическую организацию файлов и навигационные связи по-прежнему определяет основной агент.

Несколько материалов можно обработать пакетно; результат каждого материала проверяется отдельно. Технические данные нарезки не создают файлов knowledge. Смена токенизатора, размера окна или перекрытия требует повторной автоматической подготовки затронутого индекса по сохранённым материалам, без участия агента в выборе границ. При неизменных тексте, профиле эмбеддингов и настройках нарезки повторная индексация не нужна.

Изменившийся текст помечается ожидающим подготовки. Старые части не выдаются за актуальное содержание новой ревизии. Ошибка токенизации, провайдера или записи индекса не уничтожает исходный материал: он остаётся доступен для точного чтения, а незавершённая подготовка сохраняется для продолжения. Возобновление использует сохранённый текст и настройки; возвращать работу по нарезке основному агенту или субагенту не требуется. Изменение только ссылок или пути файла не требует новых эмбеддингов.

## 6. Как основной агент использует поиск

Основной агент формулирует запрос по сведениям, необходимым для текущей работы, либо по новым фактам, которые нужно сопоставить с накопленными. Запрос не обязан происходить из возврата субагента.

Плагин вычисляет вектор запроса совместимым с материалами профилем. Для Qwen применяется формат:

```text
Instruct: Given a query, retrieve relevant technical documentation.
Query: Что происходит с готовым CSV-файлом при ошибке записи?
```

Инструкция на английском задаёт задачу поиска; сам вопрос может быть на русском. Исходные части материалов передаются модели без этой поисковой инструкции. Векторы запросов не становятся материалами knowledge.

Выдача ограничивает круг кандидатов и возвращает их ID, текущие адреса и расстояния. Основной агент читает подходящие материалы и только необходимые связанные сведения. Поэтому каждый сохранённый файл должен быть самостоятельным смысловым блоком: для ответа про один предмет не должно требоваться читать весь исходный отчёт.

Векторная близость помогает отбору, но не гарантирует наличие ответа. Пустая выдача не доказывает отсутствие знания. При недостатке сведений основной агент меняет запрос, использует точные ссылки либо исследует разрешённые источники сам или с помощью исполнителя. Не вводится обязательное чтение всей базы. Ограниченная выдача осознанно не гарантирует абсолютную полноту поиска.

### Отбор кандидатов для одного запроса

Кандидат на этом этапе — вектор токенного фрагмента исходного текста со ссылкой на материал knowledge. Расстояние `d` измеряется от вектора запроса: чем оно меньше, тем ближе кандидат.

Предварительно приняты три ограничения:

- `N` — максимальное число ближайших векторных результатов, запрашиваемых у базы для одного запроса. Лимит выбирается по допустимому объёму контекста. Это ограничение возвращаемых результатов, а не количества векторов, которые база может обработать внутри поиска.
- `d_max` — максимально допустимое расстояние. Результаты дальше этой границы отбрасываются, даже если они ближайшие среди имеющихся в базе.
- Скачок расстояния — граница внутри полученной выдачи, после которой кандидаты заметно дальше от запроса.

Последовательность выполняет код плагина, без дополнительной языковой модели:

1. Запросить у LanceDB не больше `N` ближайших результатов, упорядоченных по возрастанию расстояния. На этом этапе получить расстояния и ссылки; тексты всех материалов knowledge для вычисления границы не нужны.
2. Отбросить результаты с `d > d_max`. Если ничего не осталось, вернуть пустую выдачу. Пустая выдача означает отсутствие прошедших отбор кандидатов для данного запроса, а не доказанное отсутствие сведений в knowledge.
3. Для оставшегося списка вычислить разницы расстояний между соседями. Взять медиану положительных разниц и определить порог скачка как большее из минимальной величины скачка и медианы, умноженной на заданный коэффициент.
4. Найти первый соседний промежуток не меньше этого порога. Оставить результаты перед ним; более далёкий кандидат, образующий скачок, и всё после него не передаются агенту. Например, в списке `0,10; 0,11; 0,12; 0,35; 0,36; 0,37` при пороге скачка `0,03` остаются первые три результата.
5. Если скачка нет, вернуть все оставшиеся результаты: они уже прошли `d_max`, а их количество не превышает `N`. При числе результатов меньше трёх или отсутствии положительных разниц отсечение по скачку не применяется.
6. Убрать повторяющиеся ссылки на один материал knowledge. Основной агент читает содержание отобранных материалов и сам решает, какие сведения совпадают, дополняют друг друга или различаются.

За основу взято отсечение из `reference-analytics/vectorstore.py`, функция `_search_collection`. В исследованном коде минимальный скачок равен `0,02`, коэффициент при медиане — `3`. Эти значения не утверждены как настройки для Qwen и материалов PCW. В отличие от исходного вызова `get_context`, здесь запрашивается ограниченная выдача, а не вся коллекция; медиана рассчитывается после фильтра допустимого расстояния по оставшимся результатам этой выдачи.

### Отсутствие скачка и продолжение поиска

Если скачка нет, действует фиксированный верхний лимит `N`. Достижение лимита не означает, что следующие кандидаты нерелевантны: это ограничение объёма одного ответа. Слабый хвост прежней выдачи не добавляется ради расширения поиска. Основной агент при необходимости меняет формулировку или акцент запроса, получает новую выдачу и использует её с теми же правилами отбора. Уже прочитанные неизменившиеся материалы повторно читать не требуется.

Для зафиксированного проверочного корпуса PCW с локальной Qwen указанной ревизии и косинусным расстоянием выбран калиброванный стартовый профиль: `N=10`, `d_max=0,45`, минимальный скачок `0,01`, коэффициент `2`. Подбор выполнен по 24 запросам с полезными и явно неподходящими совпадениями; отдельные 12 запросов использованы после выбора только для оценки. Полные ответы найдены для 6 из 8 положительных проверочных запросов; все 4 отрицательных отклонены. Для русских положительных запросов результат — 2 из 4. Область и воспроизведение описаны в [отчёте](search-assessment.md). Эти значения относятся к проверочному корпусу и прежней подготовке частей; они не подтверждают качество токенных окон с перекрытием и не меняют автоматически настройки существующих workspace или общие значения по умолчанию. Для другого корпуса, модели, метрики или способа нарезки требуется отдельный подбор.

Дополнительное отсечение «плато» из исходного MCP не считается автоматически утверждённой частью этой схемы. В исходном коде для него достаточно одной близкой пары кандидатов на удалении от начала выдачи; устойчивость ровного хвоста не устанавливается. При отсутствии скачка согласованное ограничение — `N` вместе с `d_max`, а не это дополнительное правило.

## 7. Когда и как уплотняется knowledge

Уплотнение входит в обработку новых знаний и поправок, независимо от того, кто исследовал внешний источник. Не требуется сначала сохранять целиком каждый сырой возврат или создавать дублирующий отчёт. Основной агент работает с новыми фактами и уже прочитанным контекстом; недостающие материалы находит через поиск и ссылки.

1. Определить, что новый результат дополняет, изменяет или повторяет. Сопоставить содержание затронутых материалов: близость векторов сама по себе не является основанием для объединения.
2. Не создавать ещё одну копию полного повтора. Новые подробности включить в подходящий материал, если сохраняются его самостоятельный предмет, условия и полезные прежние сведения. Независимые предметы сохранить отдельными файлами.
3. Для повторяющегося описания, нужного нескольким материалам, рассмотреть общую часть со ссылками. Не стирать различия версий, окружений, условий и наблюдавшихся результатов ради объединения.
4. Исправить установленную ошибку в действующем описании. Неразрешённое противоречие сохранить с его основаниями и неопределённостью, не превращая его в согласованный факт.
5. Основному агенту самому сохранить итоговые тексты и ссылки через MCP. При полной замене передать явное соответствие старых ID итоговым; плагин механически применяет решение по разделу 8.
6. Подготовить новые и изменённые материалы к поиску по разделу 5. Не пересчитывать эмбеддинги неизменившихся текстов.

### Оценка стоимости размещения сведений

Сравниваются два разных показателя: объём сохраняемого текста и объём контекста, который потребуется прочитать для конкретного вопроса. При начальном разделении на самостоятельные предметы цель — не заставлять читать ненужные разделы; небольшое увеличение служебных данных не оправдывает сохранение общего многотемного отчёта.

При выделении повторяющейся общей части учитываются общий текст, неповторяющиеся остатки, списки ссылок, служебные данные и необходимость дополнительных чтений. На коротком повторе отдельный материал и ссылки могут обходиться дороже повторения — тогда такое выделение не применяется. Подсчёт может выполнить основной агент доступными инструментами; обязательный исполнитель для него не нужен.

Если есть данные о прошлых обращениях, сравнение читаемого контекста проводится на тех же запросах с учётом необходимых переходов по ссылкам. Без таких данных экономия чтения не выдаётся за измеренную. Например, замена 1 000 токенов на общую часть в 400, различия в 200 и служебные данные в 30 даёт 630 токенов хранения, но сама по себе не доказывает экономию чтения или сохранность смысла.

Общий размер хранилища оценивается отдельно: буквальные части в LanceDB и векторы также занимают место. Уменьшение Markdown нельзя автоматически объявлять уменьшением всей базы.

Уплотнение меняет рабочие материалы. Дополнительная сводка рядом с оставленными повторами не заменяет его. Сведения не удаляются только потому, что не понадобились текущей задаче; обязательной переработки всей базы после каждого результата нет.

Сохраняются полезные контракты функций, порядок операций и сохранения, переходы состояния, защита от гонок, исключения и условия применимости. Их нельзя заменять отметкой «исправлено», списком тестов или ссылкой на Git. История и проверки дополняют актуальное содержание knowledge.

## 8. Связи и переходы между материалами

### 8.1. Принятое назначение связи

Ссылка — навигационный указатель: связанный материал может быть полезно открыть вместе с текущим. Она не является утверждением «зависит от», «является частью», «противоречит» или гарантией применимости сведений. У ссылки нет обязательного типа отношения, текстового пояснения, оценки уверенности или собственного эмбеддинга.

Основной агент определяет ссылки при работе с содержанием knowledge, и сам записывает их через MCP. Он не обязан формулировать и затем постоянно актуализировать отдельный смысл каждой связи. Условия, ограничения и реальные зависимости, необходимые для задачи, описываются в содержании материалов; их нельзя заменять одним наличием ссылки.

Граф служит продолжением поиска, а не гарантированно актуальной схемой зависимостей. Это осознанное ограничение выбранной схемы: постоянная проверка смысла всех отношений при изменении текста не вводится. Применимость прочитанных сведений основной агент оценивает при их использовании для конкретной задачи.

### 8.2. ID, место хранения и форма ссылки

ID нового материала генерирует MCP. Этот ID становится именем файла с расширением `.md` и возвращается вызывающему агенту. `pcw_create` принимает содержание и ссылки, без выбранного агентом имени. Дополнение текста, исправление сведений, смена заголовка и перемещение в другой каталог сохраняют ID. Совершенно иной по предмету материал получает новый ID от MCP. Существующие имена автоматически не изменяются.

В служебном YAML-блоке в начале файла knowledge хранится `links` — список имён файлов материалов, к которым можно перейти; без ссылок список пуст. Второе поле `id` для отдельной идентичности не требуется: сгенерированный MCP идентификатор уже является именем файла.

Это служебный список записи, а не шаблон её смыслового содержания. Текст, таблицы и код остаются свободными по структуре. Все материалы используют единый распознаваемый формат `links`; процедура работы со ссылками изменяет этот список, а не ищет произвольные упоминания в тексте.

Началом ссылки является материал, в чьём списке она записана; концом — материал с указанным ID. Один материал может иметь несколько ссылок и получать ссылки от нескольких других материалов. В одном списке один целевой ID хранится один раз. Ссылка на сам материал не добавляется. Создание исходящей ссылки не требует создавать зеркальную ссылку в другом файле.

Источник истины для ссылок — исходные файлы knowledge. Отдельные синопсы, файлы отношений и самостоятельная таблица графа не требуются. При наличии разрешения история изменений материалов и списков ссылок сохраняется через Git.

Инструмент чтения разрешает имя-ID в текущий путь файла. Для этого используются адресные данные о материалах, уже необходимые поисковой базе; их можно восстановить из файлов knowledge. При перемещении плагин обновляет путь в адресных и поисковых данных, сохраняя имя-ID и входящие списки `links`. Изменение существующих ID относится к отдельно порученной миграции. Неизменившийся текст повторно не делится и не получает новые эмбеддинги.

### 8.3. Кто отвечает за создание и изменения

Основной агент:

- Решает, какие материалы полезно связать в рамках выполняемой работы с knowledge.
- Сопоставляет новые факты из собственной работы, сведений пользователя или необязательных исполнителей с накопленными знаниями; определяет итоговое содержание при объединении и выделении общих описаний.
- Сам вызывает MCP для записи выбранного содержания и создания или удаления ссылок по точным ID.
- При замене материалов указывает, какие прежние ID заменены какими итоговыми ID. Плагин не выводит это соответствие из похожести текстов или из совпадения по времени удаления и создания файлов.

Все эти операции выполняет основной агент через MCP и проверяет их результат. Субагенты не получают ID и пути памяти и не выполняют её обслуживание.

Инструменты плагина:

- Выполняют отдельные процедуры создания ссылок и их переназначения или удаления.
- Находят входящие ссылки по точному совпадению ID в списках `links`.
- Меняют списки ссылок и адресные данные, не переписывая содержательные утверждения от себя.
- Не объединяют знания вместо основного агента и не поручают языковой модели массовую механическую замену ID.

Алгоритм нарезки и модель эмбеддингов в назначении ссылок не участвуют. Близость векторов может привести основного агента к материалу, но сама не создаёт ссылку.

### 8.4. Отдельная процедура создания ссылок

Процедура вызывается, когда основной агент уже выбрал связанные материалы при добавлении результата, актуализации или уплотнении knowledge. Отдельного обязательного прохода по всей базе для связывания каждой пары материалов нет.

1. Основной агент сохраняет новые смысловые материалы или изменения существующих через MCP. Новый материал получает сгенерированный ID до создания ссылок на него. Это не зависит от наличия внешнего исполнителя или зарегистрированного поручения.
2. Основной агент передаёт инструменту выбранные ID исходного и целевых материалов. Отдельное пояснение к каждому ID не требуется.
3. Инструмент добавляет целевые ID в `links` исходного материала, сохраняя остальные ссылки. Повторные добавления не создают дубликаты; неизвестный ID не превращается в ссылку на приблизительно похожий материал.
4. Изменения списков сохраняются в knowledge. Если содержательный текст не изменён, повторная токенная нарезка и вычисление эмбеддингов не требуются.

Удаление отдельной ненужной ссылки также задаётся точными ID исходного и целевого материалов. Оно не означает удаления целевого материала или других ссылок на него.

### 8.5. Как основной агент использует ссылки

1. Векторный поиск возвращает ограниченный круг материалов для текущей задачи. Основной агент читает выбранный материал вместе с его списком `links`.
2. Если сведений недостаточно, использует ID из списка как адреса следующего чтения. Инструмент может показать заголовки целей, прочитанные из соответствующих материалов, без отдельного составления пояснений отношений.
3. Инструмент открывает материал по точному ID. Новый векторный запрос и повторное прохождение порога близости для этого перехода не нужны.
4. Основной агент читает фактическое содержание. Само наличие ссылки не разрешает переносить условия или ограничения одного материала на другой.
5. Ссылки открытого материала могут стать следующим шагом чтения, даже если сам материал не попал в первоначальную векторную выдачу.
6. Основной агент использует полученные сведения в своей работе. При выбранном делегировании передаёт нужные факты текстом, без координат памяти. По собственным наблюдениям или результату исполнителя сам определяет и сохраняет необходимые уточнения knowledge.

Не требуется обходить весь граф. Чтение прекращается, когда сведений достаточно для текущей задачи. Уже прочитанный неизменившийся материал не читается снова при попадании в цикл ссылок. Если навигация не дала нужного содержания, основной агент уточняет векторный запрос либо исследует разрешённые реальные источники сам или с помощью исполнителя.

Разрешение ID даёт точный адрес, но не доказывает актуальность содержания. Если указанный материал не найден, инструмент сообщает об отсутствующем ID, а не подменяет его ближайшим векторным результатом. Основной агент может искать нужное знание отдельно; это не автоматическое переназначение сломанной ссылки.

Ссылки на реальные файлы проекта не входят в эту процедуру навигации между знаниями. Основной агент может исследовать эти файлы сам либо делегировать по правилам своей среды и действующим разрешениям.

### 8.6. Обычное изменение материала без смены ID

Дополнение и исправление содержания не запускает обход всех входящих и исходящих ссылок для повторного определения их смысла. Навигационные списки сохраняются, если основной агент не дал отдельного распоряжения их изменить. Обновляется поисковое представление изменившегося содержания, а не всей связанной области knowledge.

Если при выполнении задачи основной агент обнаружил бесполезную ссылку, он сам удаляет её через MCP. Если обнаружены неверные сведения в другом материале, они актуализируются по разделу 9. Ни то ни другое не становится обязательной проверкой всех соседей после каждой записи файла.

Отсутствие проверки смысла ссылок не означает запрета содержательно обновлять несколько материалов, когда новый результат действительно касается их всех. Но сама связь не служит основанием автоматически переписывать соседние записи.

### 8.7. Отдельная процедура переназначения при объединении или полной замене

Основной агент принимает и сам применяет решение об объединении через MCP. Плагин получает готовый итоговый текст и явное соответствие заменяемых ID; он не определяет содержание результата.

1. Основной агент определяет итоговое содержание. Он может выбрать дополнение одного из существующих материалов с сохранением его имени-ID либо создание нового материала под новым именем.
2. Основной агент передаёт MCP итоговое содержание и соответствие: каждый заменяемый ID → ID итогового материала. Такое перенаправление означает выбор итогового материала как навигационной замены прежнему.
3. Плагин сохраняет итоговый материал. Для полного объединения переносит в него исходящие списки объединяемых материалов, если агент не задал иной итоговый список. Удаляет повторы и ссылки, которые после переназначения ведут на сам итоговый материал.
4. Плагин находит все входящие ссылки на заменяемые ID. Для первой схемы достаточно программного прохода по служебным спискам `links` в knowledge и точного сравнения ID. Это не чтение всей базы основной моделью, не векторный поиск и не ручное ведение списка обратных ссылок.
5. В найденных списках плагин заменяет старые ID на заданные итоговые ID, убирает дубликаты и возникшие ссылки на сам материал. Произвольный текст и ссылки на реальные файлы эта механическая замена не затрагивает.
6. После сохранения итогового материала и переназначения ссылок плагин удаляет заменённые материалы и их поисковые записи, обновляет адресные данные и поисковое представление результата. Материалы, в которых изменился только список `links`, не требуют пересчёта эмбеддингов.

Постоянные файлы-перенаправления для каждого старого ID не создаются: действующие ссылки переписываются на итоговые ID, а история прежних состояний сохраняется через Git только при наличии разрешения. Старые файлы не удаляются раньше переназначения действующих ссылок. При ошибке сохранения операция не считается завершённой; плагин сообщает, какие изменения успели примениться, вместо сообщения об успешном объединении.

Для частичного переноса сведений, при котором исходный материал продолжает существовать, массовая замена всех ссылок не применяется. Основной агент определяет нужные новые переходы и задаёт их отдельной процедурой создания ссылок. Если один удаляемый материал заменяется несколькими и нельзя указать единственного адресата, агент явно задаёт необходимые переназначения; плагин не выбирает цель по векторной близости.

### 8.8. Удаление материала без замены

1. Основной агент принимает содержательное решение об удалении и сам вызывает MCP с точным ID. Процедура обслуживания ссылок не принимает решение об удалении знания.
2. Плагин точным поиском находит этот ID в списках `links` других материалов и удаляет соответствующие элементы списков.
3. После сохранения изменённых списков удаляет сам материал, его поисковые записи и текущие адресные данные. Его исходящие ссылки исчезают вместе с материалом; материалы, на которые он ссылался, не удаляются.

При навигационном назначении ссылок не требуется отдельно согласовывать смысл каждой удаляемой входящей ссылки: распоряжение удалить материал без замены включает техническое удаление переходов к нему. Это отличается от обслуживания графа зависимостей, где удаление ребра не устраняет зависимость.

Плагин не делает вывода, что содержание всех оставшихся материалов стало правильным после удаления ссылок, и не переписывает его автоматически. Если основному агенту известно, что удаление связано с неверными утверждениями в других материалах, их исправление относится к содержательной актуализации knowledge.

### 8.9. Обратный поиск и границы автоматизации

Входящие ссылки находятся из тех же списков, которые сохранены в исходных файлах. Для создания связи не нужно одновременно вести прямую ссылку, зеркальную ссылку и отдельную запись графа. Программный поиск входящих ссылок входит в процедуры переназначения и удаления, а не в отдельную работу основной модели.

Автоматизируются адресация, точный поиск ID, запись списков, устранение дубликатов и применение явно заданных замен. Решение связать материалы, содержательное объединение, выбор замены и удаление знания остаются у основного агента.

Эти операции плагин выполняет по запросу основного агента, без постоянного фонового процесса, контрольных сумм источников, отдельного журнала хода работы или обязательного смыслового обхода графа.

## 9. Актуализация при расхождении с реальностью и фактические проверки

Knowledge — накопленное описание, а не гарантия неизменности окружения. Основной агент использует его прежде всего, но проверяет существенные для задачи утверждения по реальным источникам, когда это требуется по характеру работы или обнаруженному расхождению. Проверку может выполнить сам основной агент либо выбранный исполнитель. Повторная проверка всех источников перед каждой задачей не требуется.

### Обнаруженное расхождение

1. Установить причину в разрешённых границах. Неверный путь, изменившийся интерфейс, отсутствие доступа и ошибка выполненной команды — разные причины. Неудача сама по себе не доказывает устаревание knowledge.
2. Продолжить работу с учётом установленного состояния, если это укладывается в запрос. Если нужны отсутствующее разрешение или решение пользователя, сохранить установленные факты и конкретный блокер. Не расширять задачу вслед за предположением.
3. Отделить наблюдение от гипотезы и указать условия, источник и способ проверки. При делегировании исполнитель возвращает фактическую поправку к переданным ему сведениям; ID памяти ему не нужны.
4. Основному агенту сопоставить новое наблюдение с затронутым контекстом и самому исправить действующие материалы через MCP. Не оставлять заведомо неверный активный текст только потому, что рядом сохранена уточняющая заметка.
5. Сохранить различия исторических наблюдений, если они относятся к другим версиям или условиям. Подготовить изменённые тексты к поиску. Не запускать обязательный пересмотр всех соседей по ссылкам.

### Достаточная проверка результата

Способ проверки выбирается по требуемому результату: чтение фактического файла, проверка ссылок, исследование данных, воспроизведение поведения или уместные тесты. Утверждение исполнителя об успехе и служебный статус MCP сами по себе не подтверждают результат внешней работы.

Проверка нужна в существенные для задачи моменты и при выявленном несоответствии. Она не обязана быть отдельным поручением субагенту и не запускается автоматически после каждого возврата или сохранения материала. Уже выполненная подходящая проверка используется повторно без её воспроизведения ради формального этапа PCW.

Для небольшой правки заметки может быть достаточно прочитать результат и проверить ссылки и сохранность прежнего содержания. Сохранность сравнивается с фактическим состоянием до разрешённой правки, а не автоматически с Git HEAD. Для утверждения о работающем поведении требуется подходящая фактическая проверка; статическая инспекция, успешная сборка и проверка опубликованного экземпляра имеют разные границы доказательства.

В память попадают полезные наблюдения, метод, условия и пределы проверки. Служебная последовательность вызовов и сообщение «проверено» без фактов не заменяют их. Неполный результат не считается принятым; уточнение получают подходящим способом, в том числе прямым чтением основным агентом. Ради этого не требуется создавать файл с техническим отчётом в knowledge.

### Незавершённость и ограничения

Незавершённая задача не должна приводить к потере уже установленных знаний. Предположение о причине сбоя нельзя записывать как доказанное исправление. Непроверенные условия сохраняются как непроверенные, а известные расхождения не скрываются статусом завершения.

Полнота обнаружения ошибок зависит от объектов, условий и способов проверки. Универсальная автоматическая проверка актуальности всей памяти не определена. Отдельный постоянный агент проверки памяти не вводится.

## 10. Сквозной пример

Пример условный. Имена ниже обозначают темы; реальные имена-ID генерирует MCP.

1. Пользователь просит изменить правило формирования CSV. Основной агент открывает Current, ищет контекст по CSV и читает найденный материал. По ссылке открывает общую процедуру сохранения через временный файл и переименование. Описание JSON целиком для этой задачи не требуется.
2. По контексту определяет нужный участок проекта, сам читает разрешённый источник и обнаруживает, что функция перемещена. Проверяет новое расположение, в разрешённых границах меняет правило и проверяет полученный CSV. Запуск внешнего исполнителя для этого не обязателен.
3. Выделяет новые знания: актуальное расположение функции, изменённое правило, условия проверки. Сам обновляет материал о CSV с сохранением ID. Если общая процедура не изменилась, не переписывает её и сведения о JSON.
4. Если исследование дополнительно выявило самостоятельные правила обработки ошибок, основной агент сохраняет их отдельным материалом и связывает с CSV и общей процедурой, когда такие переходы полезны. Не создаёт общий файл с историей всех действий.
5. После сохранения плагин автоматически нарезает изменённые материалы по токенам с перекрытием, получает эмбеддинги от Qwen или другого настроенного источника, проверяет ревизии и обновляет соответствующие записи. Основной агент не готовит части и не передаёт текст для нарезки повторно.
6. Проверяет статусы памяти, обновляет Current и сообщает пользователю фактический результат и ограничения проверки. В следующей сессии запрос про правило CSV приводит к короткому самостоятельному материалу и нужным ссылкам.

Если пользователь или среда предпочитает делегирование, второй шаг можно поручить исполнителю. Основной агент передаёт необходимые факты текстом, получает результат и выполняет те же действия с памятью. Остальной цикл и требования к качеству контекста не меняются.

## 11. Что не входит в эту схему

- Определение и регистрация окружения агента, сбор доступных моделей и инструментов, снимки окружения и карты запуска исполнителей.
- Обязательное выполнение внешнего исследования, изменений и проверок через субагентов; обязательные модельные профили исполнителей, реестр их поручений и привязка сессий как условия пользования памятью.
- Запуск исполнителей средствами PCW, отдельный контроллер всей задачи или автоматическое выполнение будущей задачи только из-за подготовки контекста.
- Передача исполнителям управления knowledge, Current, ссылками, уплотнением, удалением или Git-checkpoint памяти.
- Обязательное предварительное сохранение полного сырого отчёта, копии внешнего артефакта или истории работы в knowledge.
- Обязательный посредник для поиска и чтения контекста основным агентом; отдельная фактическая проверка после каждого возврата.
- Заявление о технической изоляции файлов и инструментов на основании одного запрета в поручении.
- Замена самостоятельных смысловых файлов большой общей заметкой с мелкими эмбеддингами; замена полных материалов одними векторами или пересказами поисковых частей.
- Определение границ эмбеддингов основным агентом, субагентом или отдельной языковой моделью; обязательная передача массивов частей при сохранении обычного материала.
- Автоматическое содержательное объединение плагином, выбор адресата замены по сходству текстов, обязательные типы и пояснения каждой ссылки.
- Самостоятельное хранилище графа наряду со списками `links`, ручное ведение зеркальных обратных ссылок или обязательный смысловой обход всех соседей после записи.
- Контрольные суммы всех внешних источников, постоянный мониторинг зависимостей или специальный проверочный сценарий для каждого вывода как универсальная гарантия актуальности.
- Наращивание иерархии сводок без устранения повторов, переиндексация неизменившихся материалов и сохранение служебных квитанций с последующей индексацией.
- Объявление результата верным только по наличию регламента, успешному ответу MCP или прохождению отдельных тестов.

## 12. Отложенное решение

Правила автоматического обнаружения незаметных расхождений между knowledge и реальностью не определены. До появления отдельного согласованного решения действуют обращение прежде всего к накопленному контексту, проверка существенных фактов по необходимости и актуализация обнаруженных расхождений. Отсутствие автоматического мониторинга не отменяет обязанность сохранять установленную поправку.

## 13. Требования к реализации и проверке этой версии

Этот раздел задаёт критерии будущего соответствия. Само создание документа не означает изменения runtime, MCP-схем, skill или установленного плагина.

### Память без обязательного управления исполнителями

- Чтение, поиск, создание и обновление знаний, ссылки, Current и подготовка поиска доступны основному агенту без определения или регистрации окружения, регистрации внешнего поручения, карты моделей исполнителей и ID субагента.
- Прямые наблюдения основного агента сохраняются с реальным происхождением, без фиктивного возврата исполнителя. Необязательное делегирование не меняет владельца памяти.
- PCW не навязывает способ запуска, отдельного проверяющего или порядок распределения внешней работы. Токенная нарезка и получение эмбеддингов автоматически следуют за сохранением текста по разделу 5; служебное состояние подготовки не превращается в общий контроллер внешних задач.
- Операции записи проверяют ревизии и фактическое сохранение; пакетные вызовы показывают частичные ошибки. Повторное чтение и повторная передача неизменившихся инструкций не становятся обязательной платой за каждый вызов.
- Незавершённая подготовка и известные ошибки памяти не скрываются успешностью внешней задачи. После восстановления из файлов или разрешённого Git-отката адреса, ссылки и поисковые данные приводятся в соответствие материалам.
- Git-checkpoint выполняется только при действительном разрешении. Отсутствие запрета не заменяет разрешение; неавторизованный коммит не становится условием завершения работы с контекстом.

### Сквозные проверки

1. **Работа основного агента напрямую:** восстановить Current, найти нужный материал, самостоятельно исследовать разрешённый источник и сохранить новые факты отдельными смысловыми блоками. Весь цикл проходит без определения окружения, сбора моделей и инструментов, внешнего рабочего субагента, регистрации его поручения и идентификатора исполнителя.
2. **Формирование и поиск:** сохранить обычный материал цельным текстом, автоматически нарезать его токенными окнами с перекрытием и записать эмбеддинги без помощника и передачи границ основным агентом. Выполнить запрос по одному предмету: он должен приводить к соответствующему материалу и нужным ссылкам, а не требовать чтения общего многотемного отчёта.
3. **Актуализация:** исправить известное неверное утверждение в рабочем тексте, сохранить условия и полезные детали, обновить только изменённые поисковые записи. Проверить неизменность ID и отсутствие прежней ревизии в текущей выдаче.
4. **Связи и восстановление:** проверить создание, перемещение, объединение и удаление по точным ID, отсутствие потерянных ссылок при штатном завершении, честный частичный статус при ошибке и продолжение незавершённой подготовки.
5. **Необязательное делегирование:** если проверяется этот вариант, передать исполнителю достаточные факты без координат памяти и получить результат. Все операции PCW выполняет основной агент. Успешное соблюдение поручения в одном запуске не объявляется технической изоляцией.
6. **Токенная нарезка:** проверить размер окна, перекрытие, шаг, короткий и пустой текст, последнее окно, недопустимые параметры и полное покрытие без потери символов, в том числе на русском тексте, таблицах и коде. Проверить устаревшую ревизию, ошибку провайдера и отсутствие новых эмбеддингов при изменении только ссылок. Служебные результаты не создают knowledge-файлы.
7. **Сменный источник:** проверить Qwen по умолчанию, замену на другую локальную модель и API эмбеддингов с ключом, совместимость токенизатора и лимитов входа, переиндексацию при смене профиля или настроек нарезки. Запросы и материалы должны использовать совместимые векторы; ошибка переключения сохраняет прежний рабочий индекс.
8. **Обычная небольшая задача:** измерить полный цикл, включая время, вызовы, переданный контекст и фактический результат. Размер отдельного ответа MCP или скорость искусственного теста не доказывают ускорение пользовательской работы.
