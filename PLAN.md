# Persistent Context Workspace

Status: the plugin MVP is implemented; the long-running scenarios in Phase E have not yet been completed. This file is the living implementation plan. Record architecture changes here before implementing them.

## 1. Purpose

The project provides a portable memory layer for long-running agent work on semantic subprojects. It borrows RLM ideas—external context, selective reading, and delegation—but adapts them to a session-based agent environment in which work lasts for weeks and includes real file changes.

The system must:

- preserve continuity across sessions;
- avoid loading the entire history into the primary agent;
- separate temporary cycle results from durable knowledge;
- progressively compact the current state instead of appending forever;
- retrieve details through links only when needed;
- use ordinary files, Git, and native agent tools;
- isolate the memories of unrelated subprojects;
- remain usable outside Codex.

The system must not become a log of every message, a copy of the source project, or an unbounded collection of reports.

## 2. Core model

Each semantic subproject has three memory layers:

1. `current.md` is a compact snapshot of the active working state.
2. `tmp/` contains raw and intermediate material from an unfinished cycle.
3. `knowledge/` contains linked durable knowledge that `current.md` can reference.

Git stores meaningful versions of `current.md` and `knowledge/`. Information removed during compaction therefore does not have to remain in the current file; it can be recovered from history when needed.

The state transformation is:

```text
old current + new tmp + relevant knowledge
                    ↓
       new current + knowledge changes
```

This is not a summary of the entire conversation. It is a state transformation: preserve active meaning, move durable detail into knowledge, and remove repetition and completed operational noise.

## 3. Workspace location

Memory lives in a hidden directory under the working project:

```text
<work-root>/.pcw/
├── project-a/
├── project-b/
└── project-c/
```

One directory represents one semantic subproject, not one session. Consecutive sessions for the same work reuse the same directory. Independent tasks do not share memory.

Proposed subproject layout:

```text
.pcw/<subproject>/
├── current.md
├── knowledge/
│   ├── index.md
│   └── ...
├── tmp/
│   └── <cycle-id>/
│       ├── manifest.md
│       ├── findings/
│       ├── work/
│       └── handoff.md
└── .gitignore
```

In the first implementation, each subproject memory is its own local Git repository. This isolates memory history from source-code history and keeps service artifacts out of the source repository. The source project's own Git repository must ignore `.pcw/`.

## 4. `current.md` contract

### 4.1. Why the earlier structure was rejected

Fixed sections such as `Current objective`, `Completed`, `Open work`, `Blockers`, and `Next action` model one stage too closely. They become stale quickly and push the next agent toward an old plan even after the user asks for different work.

In particular:

- `Next action` is often generated by an external model and is not durable truth;
- completed and remaining lists grow into a journal;
- a detailed `Blockers` section duplicates an object that is better opened through a link;
- many required sections force empty or artificial content.

### 4.2. Minimal format

`current.md` has only three stable sections:

```markdown
# Current

A dense description of the subproject and what is currently true.

# Pinned

Verbatim active user constraints and semantic boundaries.

# References

- knowledge: [[knowledge/...]]
- blocked_by: [[knowledge/...]]
- evidence: <path, URL, or source coordinate>
```

The sections mean:

- `Current` is a coherent snapshot of what the work is and what is now factually true. It is not a journal, plan, or template report. It contains only information whose absence would cause the next session to misunderstand the subproject.
- `Pinned` contains user requirements that must not be lost, weakened, or reinterpreted. Preserve them verbatim until the user explicitly changes or revokes them.
- `References` contains short typed links to detail. The content of a blocker, evidence, decision, or large technical note lives in the referenced object, not here.

Additional headings are not technically forbidden, but they are outside the contract and must not be generated automatically.

### 4.3. Content rules

Do not put these in `current.md` by default:

- assumed next actions;
- a complete execution plan;
- message chronology;
- every subagent report;
- lists of closed minor steps;
- detail already available through a durable reference;
- hypotheses that are not separated from confirmed facts.

When a dependency blocks work, add a `blocked_by` reference. Its target contains the description, evidence, owner, or release condition. Remove the reference after resolution and mark the linked record resolved or superseded.

Bound `current.md` by useful-context budget, not by section count. The initial budget is configurable; until measured, use roughly 2,000–4,000 tokens.

## 5. `tmp/`: unfinished cycle material

`tmp/` receives everything created after the last successful compaction:

- local maps and source descriptions;
- Reader results;
- Worker assignments and reports;
- evidence coordinates;
- conflicts and uncertain hypotheses;
- actual changes and verification results;
- user corrections not yet incorporated into memory.

Each cycle writes to its own directory. Files should reference sources rather than copying them in full without need.

`tmp/`:

- is not durable memory;
- is not indexed as confirmed knowledge;
- is not committed to Git;
- is not deleted before successful compaction;
- may survive an interrupted session.

Therefore, “clear tmp at session start” never means immediate deletion. The compaction procedure must first absorb residual material, validate the result, and only then remove material confirmed as absorbed.

## 6. `knowledge/`: durable knowledge

`knowledge/` stores information that may matter after a task or stage changes:

- architecture decisions and their reasons;
- stable domain constraints;
- component relations;
- verified diagnostic and testing procedures;
- significant incidents and causes;
- active external dependencies and blockers;
- pointers to primary sources.

One record covers one coherent subject. The base format is Markdown with short metadata:

```markdown
---
id: source-ingestion
status: active
tags: [source, reader]
supersedes: []
sources:
  - path/to/file:10
---

# Source ingestion

Short verified content.

## Relations

- depends_on: [[adaptive-chunking]]
- affects: [[reader-routing]]
```

JSON is not a required source format. A source may be any file type, directory, repository, URL, or other accessible object. Machine-readable fields describe a knowledge record and primary coordinates; they do not replace the primary material.

Initial retrieval uses:

- `knowledge/index.md` for major topics;
- clear filenames;
- `rg` for full-text search;
- wiki links and typed relations;
- `tags`, `sources`, and `supersedes` fields.

A vector database, graph database, or dedicated MCP is unnecessary in the first phase. Add one only after measured evidence that file search is insufficient.

## 7. Public contract skill and narrow internal skills

The system is not a collection of equal large skills. It has one public entry point: the `persistent-context-workspace` contract skill. It defines the mandatory workflow and loads small internal skills for individual operations.

An internal skill is a separate skill with its own `SKILL.md`, not a separate process and not necessarily a separate subagent. Loading one means reading its exact instructions and executing that fixed contract. Create a subagent only when the operation itself benefits from parallel or isolated work.

### 7.1. `persistent-context-workspace`: process contract

The main skill contains:

- cycle states and legal transitions;
- invariants for `current.md`, `tmp/`, `knowledge/`, and Git;
- conditions for loading each internal skill;
- the order in which results pass between operations;
- stop, recovery, and repeat rules;
- authority boundaries for the primary agent, Readers, and Workers;
- an exact sibling-file loader for internal skills.

It does not reimplement every operation as long free-form instructions. It selects the next legal transition, resolves and reads exactly one sibling internal `SKILL.md`, verifies its identity, executes it, validates the result envelope, and only then continues.

The loader must:

1. derive the plugin skills root from the path of the already-loaded main `SKILL.md`;
2. resolve `<skills-root>/<pcw-skill-name>/SKILL.md`;
3. canonicalize paths and reject escape from the same skills root;
4. read the complete file;
5. verify that frontmatter `name` matches the requested operation;
6. stop if any check fails.

This avoids relying on a textual `$pcw-*` name being rediscovered as a new runtime invocation.

Only the main contract skill:

- is a normal user entry point;
- decides whether a stage is complete;
- permits the next transition;
- binds the workflow to the current user request;
- coordinates Readers and Workers.

### 7.2. Internal skill contract

Each internal skill performs one narrow operation and declares:

- exact preconditions;
- concrete input files or parameters;
- allowed read and write scope;
- one result type;
- verifiable postconditions;
- blocker format;
- repeated-call behavior.

An internal skill does not select the next stage, widen scope, or load another internal skill. It returns control to the main contract skill.

Internal skills have `allow_implicit_invocation: false`. The main skill locates them through the exact sibling path, not implicit matching. This makes the sequence observable and repeatable.

### 7.3. Initial internal skills

- `pcw-resolve-workspace` selects one subproject memory from a path and request without changing it.
- `pcw-open-cycle` checks `current.md`, Git, and residual `tmp/`, then creates or recovers a cycle manifest.
- `pcw-inspect-source` uses cheap read-only inspection to decide whether distributed reading is needed.
- `pcw-map-source` creates a temporary map only for a large or unknown source.
- `pcw-record-result` normalizes a Reader or Worker result into the current `tmp/` cycle.
- `pcw-promote-knowledge` classifies new material and updates only `knowledge/`.
- `pcw-compact-current` rebuilds and progressively compacts only `current.md`.
- `pcw-validate-memory` validates links, budget, `Pinned`, evidence, and absorption without writing.
- `pcw-checkpoint-memory` prepares a diff and automatically creates a validated local Git checkpoint.
- `pcw-prune-tmp` removes only a cycle confirmed as absorbed by a successful checkpoint.

Add a new internal skill only for a distinct repeatable operation with its own input, output, and postcondition.

## 8. Update and compaction procedure

The main contract skill assembles a transactional cycle from narrow internal operations. No operation may declare the whole memory update complete by itself.

### Step 1. Fix the input — `pcw-resolve-workspace` and `pcw-open-cycle`

- resolve the exact semantic subproject memory;
- read the existing `current.md`;
- enumerate unprocessed `tmp/` cycles;
- inspect memory Git state;
- do not change or delete input material.

### Step 2. Classify new material — `pcw-promote-knowledge`

Classify each new meaning as:

1. active context for `Current`;
2. a verbatim durable constraint for `Pinned`;
3. durable knowledge for `knowledge/`;
4. transient detail that should not survive the cycle;
5. a conflict or uncertainty that must not be silently collapsed.

Write the classification to a promotion manifest. `pcw-compact-current` consumes that manifest and does not repeat the classification.

### Step 3. Update `knowledge/` first — `pcw-promote-knowledge`

- create a record only if no suitable record exists;
- otherwise update the existing record;
- preserve primary evidence coordinates;
- link dependent records;
- mark replaced information through status or `supersedes`;
- never promote an unconfirmed hypothesis to fact.

References needed by the future `current.md` must exist before it is rewritten.

### Step 4. Rebuild `current.md` — `pcw-compact-current`

Rewrite the file as a whole; never append a new section at the bottom.

The rebuild must:

- preserve active `Pinned` items verbatim;
- apply explicit user changes or revocations;
- merge duplicate meanings;
- remove resolved transient states;
- replace detail with knowledge or primary-source links;
- keep unresolved conflicts explicit;
- omit plans and next actions unless the user pinned them as durable constraints;
- leave enough context for a clean agent to understand the subproject without chat history.

### Step 5. Compact progressively — `pcw-compact-current`

Compact in this order:

1. remove exact duplicates;
2. merge equivalent meanings;
3. replace detailed evidence with a reference;
4. replace durable detail already promoted to `knowledge/` with a reference;
5. remove completed operational noise;
6. shorten wording without losing constraints or decision reasons;
7. if still over budget, repeat on the least active details.

Do not copy the old state into a per-cycle archive. Git provides its history.

### Step 6. Validate — `pcw-validate-memory`

Before accepting the cycle, verify that:

- every local link resolves;
- `Pinned` was neither lost nor paraphrased without evidence;
- new claims are supported by `tmp/`, existing knowledge, or a primary source;
- conflicts remain visible;
- `current.md` fits its configured budget;
- processed `tmp/` is not tracked by Git;
- a fresh agent can understand the state through `current.md` and its links.

### Step 7. Finish the transaction — `pcw-checkpoint-memory` and `pcw-prune-tmp`

Finish in this order:

1. show or save the memory diff;
2. commit only validated paths inside the selected PCW memory repository unless explicitly forbidden;
3. remove only the absorbed cycle represented by that checkpoint, without separate permission;
4. retain unabsorbed or disputed material for another cycle.

An explicit user prohibition leaves the validated changes and processed `tmp/` intact.

## 9. Working cycle

### Session start

1. The user identifies a working project or semantic subproject.
2. The main skill loads `pcw-resolve-workspace`.
3. `pcw-open-cycle` inspects existing memory and unfinished `tmp/`.
4. If an unabsorbed cycle exists, complete `pcw-promote-knowledge`, `pcw-compact-current`, `pcw-validate-memory`, `pcw-checkpoint-memory`, and `pcw-prune-tmp` in order.
5. Load `current.md` and only the references relevant to the new request.
6. Create the new cycle manifest in `tmp/<cycle-id>/`.

A new task does not inherit an old plan. It inherits the subproject's durable identity and knowledge, while the user's new request determines direction.

### Source investigation

First, `pcw-inspect-source` uses cheap methods:

- file types and sizes;
- directory tree;
- extensions and signatures;
- obvious structural boundaries;
- selective read and search support.

Read a small or clearly structured source directly. If a large or unknown source requires distributed work, `pcw-map-source` applies two-stage adaptive partitioning:

1. divide the source without loss into sequential overlapping windows;
2. let Readers identify local format and record coordinates;
3. repartition by natural objects such as log events, table rows, JSON entities, text sections, or project files;
4. merge and reread objects split at window boundaries.

The map is temporary navigation material in `tmp/`, not mandatory durable knowledge.

### Execution

Readers receive the original task so their extraction is targeted, but their reports never replace the source. A Reader result contains:

- task-relevant facts;
- exact coordinates;
- relations and dependencies;
- uncertainty;
- targeted suggestions about what warrants deeper reading.

Workers receive both reduced context and original target objects. They modify the source project. `pcw-record-result` stores a normalized account in `tmp/`: what changed, where, which checks ran, and what remains unverified.

Direct work by the primary agent is Worker activity for memory purposes even when no subagent was created. Record its final target state and checks after the work; a pre-work analysis or assignment does not satisfy this requirement. When external evidence materially affects the result, preserve its stable coordinates in the result. Promotion decides whether that meaning becomes durable knowledge, remains reachable through the changed target, or is ephemeral.

A separate Verifier is not mandatory. Integrator and Correlator roles are also not introduced by default. The primary agent connects results itself or delegates a concrete complex integration only when doing so saves context or time.

### Completion gate

Before telling the user that a task or meaningful stage is complete, the main skill must:

1. inventory every accepted source change and every external fact that materially affected the result;
2. verify that `pcw-record-result` represents the final state, checks, coordinates, and remaining uncertainty for each item;
3. compare `current.md` and relevant knowledge with the actual target state and reject any stale contradiction;
4. run promotion, compaction, and validation for all unabsorbed results;
5. complete the automatic local checkpoint and exact-cycle pruning unless explicitly forbidden.

If the user forbids the memory transaction, report source completion separately and retain recoverable inputs. Never report the PCW cycle complete while final work is missing from memory, `current.md` contradicts the target, validation has not succeeded, or checkpointing remains unresolved.

### Return-to-work gate

A memory operation is infrastructure and does not complete or replace the source task that caused it. After recovery, checkpointing, or another memory-only interruption, the main skill must identify the latest unresolved and still-authorized user task from user messages, cycle manifests, recorded results, and supported Current facts.

Treat a request to record, inspect, compact, or checkpoint memory as additive when it does not explicitly cancel, replace, pause, or narrow the unfinished source task. After memory becomes consistent, resume that task without asking the user to repeat it. Stop instead when the later request replaces the task, the user cancels or pauses it, the task is already complete, or continuation requires new authority.

An explicitly authorized unfinished operation may appear in `Current` when its absence would break continuation. Describe its exact target, authorized scope, and factual execution state declaratively. This is active state, not an inferred next action. Update or remove it when the task is completed, revoked, replaced, paused, or materially rescoped.

### Stage completion

1. All factual results exist in `tmp/`.
2. `pcw-promote-knowledge` updates durable records.
3. `pcw-compact-current` rebuilds and compacts `current.md`.
4. `pcw-validate-memory` checks the resulting state without writing.
5. Only after validation may `pcw-checkpoint-memory` run, followed by `pcw-prune-tmp` after a confirmed checkpoint.

The next session starts from a new compact snapshot and linked knowledge, not a complete activity log.

## 10. Primary-agent modes

Two modes may use the same file contract.

### Normal mode

The current primary agent is the user interface, follows the main contract skill, and executes narrow internal skills at each transition. This is simpler and cheaper for most work.

### Clean Controller

An optional subagent with minimal context reads only the request, `current.md`, and selected references. This more closely resembles RLM isolation and can help when the main conversation is contaminated or a long independent pass is needed.

The clean Controller is an option, not a mandatory intermediary. Memory format and compaction procedure remain identical.

## 11. Model selection

Select a model after cheap source inspection and operation-complexity assessment, not by permanently assigning maximum reasoning to a role.

- Luna handles high-volume simple reading, region classification, extraction under a clear schema, and quick checks.
- Terra handles ambiguous analysis, architecture relations, code authoring, and file changes.
- Sol manages the cycle, communicates with the user, and makes final decisions.

A Reader usually starts on Luna. Route an ambiguous region, cross-file inference, or design decision to Terra. Choose reasoning effort for the concrete region and increase it after the first pass when justified.

## 12. Git as memory

Git:

- stores earlier compacted states;
- shows semantic memory changes for a stage;
- supports branches for parallel directions;
- enables recovery without permanent archive copies.

Git must not store:

- the complete chat;
- raw copies of large sources;
- every subagent message;
- `tmp/` content;
- secrets or private tokens.

Validated local memory commits and exact-cycle pruning form one automatic internal transaction unless the user forbids it. Commits outside the selected PCW memory repository and every push require explicit authorization. A checkpoint message describes the semantic memory change, not a session number.

## 14. Implementation phases

### Phase A. Formats and invariants

- approve the minimal `current.md` contract;
- approve the `knowledge/` record format;
- define subproject and cycle identifiers;
- establish link and status rules;
- define a configurable `current.md` budget.

### Phase B. Main contract skill

- create `persistent-context-workspace/SKILL.md`;
- encode the cycle state machine;
- define transition preconditions and postconditions;
- define one result envelope;
- forbid bypassing memory-update order;
- describe interrupted-transition recovery;
- load internal skills through exact verified sibling paths.

### Phase C. Narrow memory skills

- create `pcw-resolve-workspace` and `pcw-open-cycle`;
- create `pcw-record-result`;
- create `pcw-promote-knowledge`;
- create `pcw-compact-current`;
- create read-only `pcw-validate-memory`;
- create `pcw-checkpoint-memory` and `pcw-prune-tmp`;
- disable implicit invocation for all internal skills;
- verify each operation's idempotency;
- verify recovery after failure between every pair of transitions.

Implement reliable memory updates before complete source analysis; otherwise results become another growing archive.

### Phase D. Sources and agents

- create read-only `pcw-inspect-source`;
- create conditional `pcw-map-source`;
- define two-stage adaptive partitioning;
- establish Reader and Worker result contracts;
- add Luna/Terra routing;
- verify a small file, a large mixed-format file, and a source-code project.

### Phase E. Long-running scenarios

- run at least 30 consecutive cycles on a test subproject;
- measure growth of `current.md`, `knowledge/`, and Git;
- verify a task change within one subproject;
- verify a parallel branch and later knowledge merge;
- verify transfer to another agent environment.

## 15. MVP acceptance criteria

The MVP is ready when:

- a new session recovers the meaning of the work without the complete chat;
- a new task does not inherit a stale next action;
- active user constraints survive repeated compaction;
- `current.md` remains bounded after dozens of cycles;
- detail is retrievable through links and `rg`;
- unconfirmed material never becomes fact;
- residual `tmp/` is safely recoverable and repeatable;
- source-project changes and memory changes remain distinguishable;
- the system works with ordinary files and Git without a required external service;
- the plugin installs and updates as one marketplace unit.

## 16. Deferred decisions

These are unnecessary for the first working prototype and must be decided from usage evidence:

- one shared memory repository versus one Git repository per subproject;
- automatic backlink generation;
- a full-text index beyond `rg`;
- vector search;
- an MCP interface;
- cross-machine memory synchronization;
- automatic branching and merge policies.

Until measured evidence requires more, prefer one public contract skill, narrow internal skills, a simple file contract, and Git.
