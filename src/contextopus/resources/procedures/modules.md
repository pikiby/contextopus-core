# Manage Contextopus modules

Use this procedure for root-local modules. Resolve the selected Core root and the module named by the user. Query `core.modules` to inspect discovered manifests, compatibility, storage state and errors. Discovery is read-only: listing or discussing a module does not authorize installation. Obtain operation signatures through `guide(operation=...)` only when unknown.

For an authorized installation from a built folder or ZIP, query `core.module_source_plan(module=<id>, source=<path>)`, inspect the preview, then execute `core.module_install(module=<id>, source=<same path>, source_revision=<preview revision>)`. Core checks portable paths, payload bytes, identity and compatibility, stages a new folder and invokes ordinary dependency, storage and activation steps. The CLI equivalent is `modules install ID --source PATH`; append `--plan` for inspection only. Packages containing a source checkout, symlinks, live state or caches must be built first. Source installation refuses an existing folder or lifecycle record; use the explicit update flow for an existing module.

For a package already placed under `<root>/modules/<id>` with `module.json` beside `package/`, call `core.module_install(module=<id>)`. This is also the retry action after reviewing a failed first install: omit `source` so retained files and data are preserved. TUI Install uses the same operation. Do not substitute a guessed module or root.

An installation request already authorizes this installation sequence; do not ask for the same approval again. If the user requested only inspection, explain the actual package and effects before asking whether to install. Packages are trusted code; the child interpreter and SQL namespace checks are not an operating-system sandbox. Do not expand an installation into unrelated host changes or client integration.

Core owns one SQLite file per module at `core/storage/modules/<module-id>.sqlite3`. A module declares `storage` compatibility and supplies ordered SQL migration files under `package/`; the author follows the installed module guide. Use the packaged migrations through Core. Do not generate ad hoc SQL, create tables manually, edit Core's databases, or build another installer. Only explicit storage apply or installation partitions an older `core/storage/modules.sqlite3` catalog; Core retains its source and recovery backup. Inspection, preparation and queries do not migrate it. Models, embeddings and RAG remain common to the root and separate from structured module data.

For an authorized update, call `core.module_update(module=<id>, source=<unpacked release directory>)`. Core stages the release, prepares dependencies and applies its schema; a previously enabled module is activated again, while a disabled module stays disabled. Preserve `data/`, `config/`, previous releases and user-modified files. Call `core.module_disable` only when requested; disabling does not delete domain records or user files. The low-level prepare/enable operations are available for diagnosis, but ordinary installation uses `module_install`.

After installation or update, inspect the result and `core.modules`, then verify one relevant operation through the shared API when the user's scope permits it. A failure or incompatible schema is not an enabled module. Report the actual error and retained state; retry the same Core operation after resolving its cause. Do not claim a successful install from folder presence, dependency preparation or a runnable command alone. Module-provided native skills require the separately requested client integration workflow.

For Core 1.5 persistent module services, a module may declare a service factory or `contextopus-service-v1` command and route operations with `service: true`. The root owner manages start/readiness and stop on disable, update or shutdown. Inspect `core.modules` service state/PID/error and the module's own job-status query; readiness alone does not prove background processing. Discovery remains passive. Check the installed Core version before using this contract.

Service authors use Core's bounded SQL transactions and optional `rag: true` SDK access. Each module file has a separate writer lock; a module transaction does not hold another file's lock. SQLite allows several connections but one writer per file; keep transactions short and do parsing, embedding and RAG work outside them. Relocation holds the root guard, drains module writes and keeps their locks through copying and switching roots. Transactions do not span module files, and SQL and RAG have separate commits: preserve durable queues/replay and deletion bookkeeping. Exact authoring and isolated verification details are in repository `docs/implementation/module-services-local.md`.
