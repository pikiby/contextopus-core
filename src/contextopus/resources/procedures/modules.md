# Manage Contextopus modules

Use this procedure for root-local modules. Resolve the selected Core root and the module named by the user. Query `core.modules` to inspect discovered manifests, compatibility, storage state and errors. Discovery is read-only: listing or discussing a module does not authorize installation. Obtain operation signatures through `guide(operation=...)` only when unknown.

For an authorized installation, call `core.module_install(module=<id>)`. Core prepares the declared dependencies, validates and applies the package's storage migrations, then enables its operations. This is the same action as CLI `modules install ID` and TUI Install. The author's folder belongs under `<root>/modules/<id>` with `module.json` beside `package/`. If the folder is absent, obtain the intended package and destination within the user's authorized scope. Do not substitute a guessed module or root.

An installation request already authorizes this installation sequence; do not ask for the same approval again. If the user requested only inspection, explain the actual package and effects before asking whether to install. Packages are trusted code; the child interpreter and SQL namespace checks are not an operating-system sandbox. Do not expand an installation into unrelated host changes or client integration.

Core owns the shared domain catalog at `core/storage/modules.sqlite3`. A module declares `storage` compatibility and supplies ordered SQL migration files under `package/`; the author follows the installed module guide. Use the packaged migrations through Core. Do not generate ad hoc SQL, create tables manually, edit Core's catalog, or build another installer. Structured module data and shared RAG are separate services; RAG remains common to the root.

For an authorized update, call `core.module_update(module=<id>, source=<unpacked release directory>)`. Core stages the release, prepares dependencies and applies its schema; a previously enabled module is activated again, while a disabled module stays disabled. Preserve `data/`, `config/`, previous releases and user-modified files. Call `core.module_disable` only when requested; disabling does not delete domain records or user files. The low-level prepare/enable operations are available for diagnosis, but ordinary installation uses `module_install`.

After installation or update, inspect the result and `core.modules`, then verify one relevant operation through the shared API when the user's scope permits it. A failure or incompatible schema is not an enabled module. Report the actual error and retained state; retry the same Core operation after resolving its cause. Do not claim a successful install from folder presence, dependency preparation or a runnable command alone. Module-provided native skills require the separately requested client integration workflow.
