This is the canonical create procedure. Use Contextopus MCP, not direct runtime writes. Workspace operations accept the legacy names below; prefer `workspace.<operation>`. Resolve the selected work_root and workspace explicitly. Fetch a referenced procedure with `procedure(name=...)`; fetch a reference with `procedure(name="reference/<name>")`.


# Create context

Use the two [MCP entrypoints](procedure:workspace#mcp-calls): `contextopus_query` for reads and `contextopus_execute` for changes. The names below are operations; place their parameters in `arguments`. Describe only an unknown signature.

1. Follow [context selection](procedure:workspace#context-selection). Establish the actual creation request and project/task scope. Accept any clear natural-language description; do not require parameter names.
2. Resolve placement. Prefer the already established common memory root; offer a concrete `<work_root>/modules/workspace/workspace_contexts/<workspace>/` there and a user-chosen location. If no root is established, offer explicit locations for the common memory root rather than deriving one from a repository name. Explain that context folders have independent rules and files while the root's RAG and analytics databases are shared. Inspect the selected path without startup. Never overwrite an existing context or merge different roots by guessing. Include needed parent-directory creation in the proposed placement.
3. Read the packaged [default instructions](procedure:default-instructions) and first offer its settings as **one standard set**, in ordinary conversation language. The standard currently means: work updates require a Workspace invocation; shown record changes do not wait for additional approval; local Git history is on; each material is limited to 1024 tokens; automatic authoring of required-source links is off (existing required sources are still checked). Explain that instructions changes require approval under the independent `instructions_approval_required: true` default. Ask one question: **Use these settings (recommended)** or **Customize settings**. Preserve any settings the user already supplied and show those overrides in the offered set. A clear acceptance selects all displayed settings; silence or a preselected option does not. Do not ask again when all values are already unambiguously supplied.
   If the user declines the set or requests customization, ask **separate questions** only for unanswered settings: `allow_implicit_updates`, `knowledge_approval_required`, `instructions_approval_required`, `git_history_enabled`, `material_max_tokens`, and `create_required_sources`. For instructions approval, offer **Yes (recommended)** and **No** separately from knowledge approval. For the size question, offer **1024 tokens (recommended)**, **Another limit**, **No limit**, in that order. Ask for a positive number only for another unspecified limit; no limit means null. For source links ask whether the agent should add references whose specified information must be freshly checked on every receipt. Do not infer this choice from general write permission. Wait for the actual answers; never treat refusal of the standard set as disabling all settings.
4. Compose initial INSTRUCTIONS using that one template and the six selected settings; compose the project record from the user's stated purpose, goals and boundaries. If source links are accepted, include the template's Required sources rule directing the agent to create them under its stated criteria. If declined, keep the setting false; no authoring obligation is enabled. Show the resulting instructions, project text, settings and absolute destination so the agreed creation is concrete. Do not import unapproved facts from chat as knowledge.
5. Call `workspace_create(request_id, instructions_content, project_content, user_request)` with those exact texts and the user's creation request. Retry identical input with the same request ID. Creation writes and indexes the initial project record, initializes no task and opens no cycle. Verify returned path, settings and independent Git status.
6. If the user also authorized actual work, begin the [work cycle](procedure:workspace#work-cycle). Otherwise report creation and stop; an empty new context needs no fabricated knowledge, proposal or finish call. Keep the established coordinates for continuation.
